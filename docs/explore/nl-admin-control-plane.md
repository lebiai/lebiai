## 1. 执行摘要

### 1.1 一句话

**把传统后台管理端的「菜单 + 表单 + API」重构为「自然语言操作台 + 生产级控制平面」：用户用对话查询、变更与生产操作；系统用强类型工具、风险分级、人机确认、幂等与审计保证可上生产。**

### 1.2 核心主张

| # | 主张 |
|---|------|
| 1 | **不是**用大模型替代业务系统，而是在业务系统之上增加 **NL Control Plane（自然语言控制平面）** |
| 2 | **能查、能写、能生产** 同时成立的前提是：**读平面 / 写平面分离** + **L0–L3 风险分级** + **唯一写入口（Command Gateway）** |
| 3 | 模型只做 **意图理解与编排**；**授权终裁在业务 RBAC**；**危险执行必须人机共批** |
| 4 | 与乐彼AI 契合路径：**MCP 工具化 + 领域 Skill + 现有 turn 确认门禁 + 本地凭证**，不必另起平行引擎 |
| 5 | 与传统后台 **互补**：复杂配置、可视化大表、权限矩阵仍用页面；高频查询、状态推进、受控变更走对话 |

### 1.3 推荐默认路径（本方案采纳）

```
目标系统稳定 API
  → Command/Query Gateway（鉴权 · 分级 · 幂等 · 审计）
  → MCP Server（强类型 Tools + 风险元数据）
  → 乐彼AI Agent（companion 协议 · Skill · run_turn · 确认 UI）
  → 用户（桌面 GUI 为主；IM 默认只读/关闭写）
```

### 1.4 明确不做（本方案边界）

- 不让模型持有生产库直连账号执行任意 SQL  
- 不提供「万能 HTTP 任意 URL」通配写工具作为默认  
- 不在 IM 群默认开放生产写  
- 不宣称「一句话无人确认即可不可逆生产变更」为默认体验  
- 不做「自动生成完整传统后台前端」的低代码平台

## 2. 背景与问题定义

### 2.1 现状痛点

传统后台管理端（Admin Console / CMS / 运营后台 / 运维控制台）普遍存在：

| 痛点 | 表现 |
|------|------|
| **路径长** | 登录 → 多级菜单 → 筛选 → 点详情 → 改字段 → 提交 |
| **认知负担** | 字段名、状态机、权限角色需培训；新人上手慢 |
| **跨系统碎** | 订单在 A、用户在 B、库存在 C，运营要开多个后台 |
| **查询贵** | 临时统计/核对往往还要找研发导出 |
| **变更惧** | 怕点错；批量操作缺乏「先预览再执行」 |
| **审计弱** | 人点的按钮日志不完整；出事难复盘「当时意图」 |

### 2.2 需求本质

将管理动作从 **UI 驱动** 变为 **意图驱动**：

```
人：自然语言意图
  → 机器：解析为受控业务命令
  → 系统：在权限与策略下执行
  → 人：获得可核对的回执与可追溯记录
```

完整需求包含三个能力档：

| 能力档 | 含义 | 典型句 |
|--------|------|--------|
| **能查** | 只读检索、聚合、导出摘要 | 「今天待发货有多少」「订单 12839 什么状态」 |
| **能写** | 变更业务状态与字段 | 「把工单指给张三」「备注写上已电联」 |
| **能生产** | 对 **生产环境** 执行真实副作用（含不可逆） | 「生产环境退款」「对 prod 触发同步任务」「封禁用户」 |

### 2.3 为何难

| 难度 | 说明 |
|------|------|
| **幻觉执行** | 模型编造 id、金额、状态导致误操作 |
| **权限漂移** | Agent 用超级账号绕过业务 RBAC |
| **重试双写** | 网络重试 / 用户重复确认导致双退款 |
| **爆炸半径** | 「关掉所有超时单」无 limit 毁数据 |
| **环境误选** | 本意 staging，打到 prod |
| **无审计** | 无法回答「谁在何时因何改了什么」 |
| **入口失控** | IM 陌生人触发写接口 |

因此：**能写能产 ≠ 放开手脚**，而是 **可治理地放开手脚**。

## 3. 目标、非目标与成功标准

### 3.1 目标（Goals）

| ID | 目标 | 用户可感知结果 |
|----|------|----------------|
| G1 | 自然语言完成目标系统的 **高频查询** | 30 秒内得到可核对答案或文件 |
| G2 | 自然语言完成 **受控写入** | 低危可顺滑；中高危有清晰确认 |
| G3 | 支持 **生产环境** 真实操作 | 显式环境、回执号、可审计 |
| G4 | 多系统可扩展 | 新系统以 Connector 接入，不改引擎核心 |
| G5 | 与乐彼「工作搭子」一致 | 推进事（Do）、有确认（主权）、可沉淀（Evolve 须批准） |
| G6 | 安全默认 | 无确认通道 fail-closed；IM 降权；密钥本地 |

### 3.2 非目标（Non-Goals）

| ID | 非目标 | 原因 |
|----|--------|------|
| N1 | 替换全部传统后台页面 | 复杂表单/可视化仍适合 GUI |
| N2 | 通用任意网站 RPA 生产运维 | 脆、难审计；仅作无 API 时的过渡 |
| N3 | 云端托管用户全部业务数据 | 与本地优先冲突（除非用户自建网关） |
| N4 | 自动批准进化候选写入 skill/memory | 服从 P0：进化须批准 |
| N5 | 第一期做完整多租户 SaaS 控制台 | 优先个人本机 / 单团队网关 |

### 3.3 成功标准（可验收）

**产品成功：**

1. 用户用自然语言完成 **至少 5 类** 真实业务查询，结果与后台页面一致  
2. 用户完成 **至少 3 类** 写入（含 1 类需确认），生产数据正确且有回执  
3. 误操作演练：拒绝确认后 **零写入**；重复提交 **不双写**  
4. 审计可回答：会话 id、操作者、环境、工具名、参数摘要、结果、确认状态  
5. 切换 staging/prod 有显式标识；默认不静默打 prod  

**工程成功：**

1. 新系统接入周期可预期（有 OpenAPI 时 ≤ 1–2 人周出只读+基础写）  
2. 工具元数据驱动确认策略，而非散落 if  
3. 与 lebi 引擎共享 turn/MCP/confirm，无平行 agent 循环

## 4. 产品定位与边界

### 4.1 在乐彼产品中的位置

乐彼AI 是 **本地工作搭子**（Do × Continuity × Care × Evolve），不是「行业垂直后台」或「运维中台 SaaS」。

本能力的产品叙事应是：

> **接上你的系统后，用对话推进管理与生产操作——该顶的时候敢顶（确认与边界），第二次更准（Skill/记忆经你批准）。**

强化爱上瞬间：

| 瞬间 | 本能力如何强化 |
|------|----------------|
| ① 被准确理解 | 领域 Skill + 先查后写，对准真实对象 |
| ② 建议像定制 | 沉淀「我们系统的口径与流程」 |
| ③ 对齐思想主轴 | 标准/禁操作进 Skill 与策略 |
| ④ 有来有回 | 冲突目标时给选项，不擅自高危写 |
| ⑤ 第二次更顺 | 成功路径进 skill 候选（须批准） |

### 4.2 与传统后台的分工

| 场景 | 传统后台 | NL 控制平面 |
|------|----------|-------------|
| 首次复杂配置、可视化编排 | ✅ 主路径 | 辅助说明 |
| 权限矩阵、角色管理 | ✅ 主路径 | 一般不开放 L3 自助改权 |
| 高频查询、核对、状态推进 | 可 | ✅ 主路径 |
| 单笔退款/封禁/重试任务 | 可 | ✅ 受控主路径 |
| 超大表浏览、拖拽排版 | ✅ | 导出摘要即可 |
| 无 API 的遗留页面 | ✅ / RPA 过渡 | 不作为生产默认 |

### 4.3 用户角色假设

| 角色 | 诉求 | 本方案策略 |
|------|------|------------|
| 个人开发者 / 小团队老板 | 自己的系统自己管 | **模式 A：本机 lebi + MCP**（主推一期） |
| 运营 / 客服 | 查单改状态 | L0–L2；L3 受限角色 |
| 运维 / SRE | 任务、发布、回滚 | Job 异步 + 环境隔离 + L3 |
| 安全 / 合规 | 审计、最小权限 | Gateway 审计 + RBAC 终裁 |

## 5. 总体方案：自然语言控制平面

### 5.1 定义

**自然语言控制平面（NL Control Plane）**：

一层介于「对话 Agent」与「业务系统」之间的控制层，负责：

1. 将意图绑定到 **已登记的业务工具**  
2. 按 **风险级别** 决定直接执行 / 确认 / 拒绝  
3. 保证 **身份、幂等、限流、审计、环境**  
4. 向用户返回 **可核对回执**  

Agent 不是上帝；控制平面是 **门卫 + 调度 + 书记员**。

### 5.2 逻辑架构（四层）

```
┌─────────────────────────────────────────────────────────────┐
│ L4  Surface（入口）                                           │
│     桌面 GUI · CLI ·（可选）Flutter · IM（默认降权）            │
└────────────────────────────┬────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────┐
│ L3  Agent Runtime（乐彼引擎）                                  │
│     companion 协议 · ContextSources · run_turn · Skill       │
│     确认桥 ConfirmRequest · Session JSONL                    │
└────────────────────────────┬────────────────────────────────┘
                             │ ToolHost / MCP
┌────────────────────────────▼────────────────────────────────┐
│ L2  Control Plane（本方案建设重点）                            │
│     Tool Catalog · Risk Policy · Idempotency · Audit         │
│     Env Router · Rate Limit · Dry-run / Preview              │
│     Command Gateway + Query Plane                            │
└────────────────────────────┬────────────────────────────────┘
                             │
┌────────────────────────────▼────────────────────────────────┐
│ L1  Systems of Record（业务系统 / 生产）                       │
│     订单 · 用户 · 库存 · CMS · 任务调度 · 配置中心 …           │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 数据与控制流（一次完整写生产）

```
用户：「生产环境，订单 12839 全额退款，原因：用户未收到货」
  │
  ├─1. Agent 加载领域 Skill + 当前环境提示（prod）
  ├─2. 先 L0：get_order(12839)  → 核实存在、金额、状态
  ├─3. 组装 refund_order 参数 + client_request_id
  ├─4. Policy：L3 → 需要确认；生成确认摘要（before/after/不可逆）
  ├─5. GUI ConfirmModal：用户 Allow / Deny
  ├─6. Deny → 零副作用；写 session 事件
  ├─7. Allow → Gateway：鉴权 → 幂等检查 → 调业务 API
  ├─8. 返回 receipt_id + after 状态
  ├─9. Agent 用人话回执；Session 落盘
  └─10. Audit 双写（session + gateway 日志）
```

### 5.4 设计原则（十条）

1. **工具封闭世界**：只能调用已登记 Tool，禁止开放世界乱写  
2. **先查后写**：高危写前必须成功读到对象真相  
3. **读写分离**：查询可走副本；写入唯一网关  
4. **级别驱动策略**：确认与否看 L0–L3，不看模型情绪  
5. **身份最小**：Agent 凭证 ≤ 操作者权限  
6. **幂等默认**：写工具必带客户端请求 id  
7. **环境显式**：prod 不可静默默认  
8. **爆炸半径受限**：批量必有 limit / preview  
9. **可观测可回放**：审计字段齐全  
10. **入口降权**：无确认 UI 的表面 fail-closed

## 6. 能力模型：能查 · 能写 · 能生产

### 6.1 能查（Query）

| 子能力 | 说明 | 必备支持 |
|--------|------|----------|
| 精确读取 | 按 id/单号取详情 | `get_*` |
| 条件检索 | 状态、时间、关键词 | `search_*` / `list_*` + 分页 |
| 计数预览 | 批量前先 count | `count_*` |
| 对比预览 | 变更前 dry-run | `preview_*` / `dry_run` |
| 导出 | 大结果落文件 | 写 workspace `outputs/` |
| 跨系统串联 | 订单→用户→物流 | 多 Tool 编排 + Skill |

**查询 SLA 建议：** 交互 P95 < 3s（网关到业务）；大导出异步 Job。

### 6.2 能写（Command）

| 子能力 | 说明 | 必备支持 |
|--------|------|----------|
| 字段更新 | 备注、标签、指派 | L1 为主 |
| 状态机迁移 | 合法 transition | 服务端校验非法迁移 |
| 创建类 | 建工单、建优惠券 | 返回新 id |
| 关联操作 | 发消息、记日志 | 可组合 Tool |
| 补偿/回滚 | 能逆则 `undo_*` | 不能逆则文案声明 |

**写入纪律：** 业务校验在 **系统 of Record**，Agent 不得「跳过校验硬写库」。

### 6.3 能生产（Production Operations）

「生产」在本方案中包括两类：

| 类型 | 例子 | 机制 |
|------|------|------|
| **P-Data** 生产数据变更 | 退款、封禁、改库存 | L2/L3 Command + 确认 |
| **P-Ops** 生产运维动作 | 跑批、同步、发布、回滚 | **异步 Job** + 状态查询 + 取消 |

生产必备：

1. **环境维度**：`dev` / `staging` / `prod`（或等价）  
2. **回执**：`receipt_id` / `job_id`  
3. **可查询进度**：长任务不可「发射后不管」  
4. **变更窗口策略（可选）**：仅允许在窗口内 L3  
5. **演练环境**：staging 全链路与 prod 同构工具集

## 7. 风险分级体系（L0–L3）

### 7.1 级别定义

| 级别 | 名称 | 副作用 | 默认可逆性 | 默认策略 |
|------|------|--------|------------|----------|
| **L0** | 只读 | 无业务副作用（可有审计读日志） | — | 直接执行 |
| **L1** | 低危写 | 可逆或低影响（备注、标签、指派） | 高 | 直接执行；可 Always Allow（会话级） |
| **L2** | 中危写 | 状态变更、配置变更、可影响资金流前置 | 中 | **必须确认**；展示 diff |
| **L3** | 高危/不可逆 | 资金、封禁、删除、批量、prod 发布 | 低/无 | **强确认** + 理由 + 可选二次门禁 |

### 7.2 分级判定规则（落到元数据）

每个 Tool 必须声明：

```text
risk_level: L0 | L1 | L2 | L3
idempotent: true | false
requires_reason: true | false
requires_object_fetch: true | false   # 执行前是否强制 get
max_batch_size: number | null
environments: [staging, prod]         # 允许的环境
side_effect: none | data | money | auth | infra
```

**升级规则（运行时）：**

| 条件 | 升级 |
|------|------|
| `env=prod` 且原 L1 | 可保持 L1 或升 L2（策略可配） |
| 批量 size > 阈值 | 升 L3 |
| 工具本身 L2 但金额 > 阈值 | 升 L3 |
| 未知工具 / MCP 外部工具 | 至少 L2，默认确认 |

### 7.3 与确认 UI 的映射

| 级别 | confirm_tx 存在 | confirm_tx 不存在（如部分 IM） |
|------|-----------------|--------------------------------|
| L0 | 执行 | 执行（若在白名单） |
| L1 | 执行 | 执行或拒绝（按白名单） |
| L2 | 弹窗确认 | **拒绝** |
| L3 | 强确认 | **拒绝** |

与乐彼 P0「无确认通道 fail-closed」一致。

## 8. 参考架构

### 8.1 组件图

```
                     ┌──────────────┐
                     │  领域 Skill  │
                     │  (Markdown)  │
                     └──────┬───────┘
                            │ 注入策略与话术
┌──────────┐  对话   ┌───────▼────────┐  tools   ┌────────────────┐
│  GUI/CLI │ ──────► │  lebi Agent    │ ───────► │  MCP Adapter   │
└──────────┘  确认   │  run_turn      │          │  (每系统一个)   │
                     └───────┬────────┘          └────────┬───────┘
                             │ session JSONL              │
                             ▼                            ▼
                     ┌──────────────┐            ┌────────────────┐
                     │ ~/.lebi-ai   │            │ Command/Query  │
                     │ 凭证 0600    │            │ Gateway        │
                     └──────────────┘            └────────┬───────┘
                                                          │
                              ┌───────────────────────────┼──────────┐
                              ▼                           ▼          ▼
                         Query API                   Command API   Job Runner
                         (只读账号)                   (写权限)      (异步)
                              │                           │          │
                              └───────────────────────────┴──────────┘
                                              ▼
                                      System of Record
```

### 8.2 Query Plane（读平面）

**职责：** 安全、快速、可缓存的读。

| 要求 | 说明 |
|------|------|
| 只读凭证 | DB 只读用户 / 只读 API scope |
| 强制分页 | `limit` 默认 20，硬顶 100（可配） |
| 字段投影 | 避免默认返回 PII 全集 |
| 超时 | 网关超时 + 熔断 |
| 缓存（可选） | L0 短 TTL；写后主动失效关键 key |
| 脱敏 | 手机号/证件默认掩码，显式 elevate 才看全量（可 L2） |

### 8.3 Command Gateway（写平面 · 唯一入口）

**职责：** 所有生产写副作用的咽喉。

| 模块 | 职责 |
|------|------|
| AuthN | 验证调用方（MCP 持有的用户/服务 token） |
| AuthZ | 映射业务 RBAC；拒绝越权 |
| Risk Gate | 校验 risk_level 与确认凭证（见下） |
| Idempotency Store | `client_request_id` → 首次结果 |
| Validator | JSON Schema / 业务规则前置 |
| Dispatcher | 调下游 HTTP/gRPC |
| Auditor | 结构化审计日志 |
| Rate Limiter | 用户/工具/全局 QPS |
| Env Router | 按 env 选上游 base URL |

**确认凭证（Confirm Receipt）：**  
对 L2/L3，Gateway 可要求请求头携带 `X-Confirm-Token`（由 Agent 在用户 Allow 后短时签发），防止绕过 UI 直打 MCP。一期可弱化为「仅经 Agent 调工具」；二期建议强化。

### 8.4 Job Runner（生产运维异步）

| API | 说明 |
|-----|------|
| `start_job(type, params, env)` | 返回 `job_id`，L2/L3 |
| `get_job(job_id)` | L0 |
| `list_jobs(filter)` | L0 |
| `cancel_job(job_id)` | L2/L3 |

状态机：`queued → running → succeeded | failed | cancelled`。

### 8.5 模式选择

| 模式 | 描述 | 适用 | 一期 |
|------|------|------|------|
| **A. 本机直连** | lebi → MCP → 业务 API | 个人/小团队 | ✅ 默认 |
| **B. 团队网关** | 多人 → 中心 BFF（OIDC）→ 业务 | 公司内网 | 二期 |
| **C. 变更单** | NL 只生成 CR，Runner 执行 | 强合规 | 按需 |

本报告实施路线以 **模式 A** 为主，架构预留 B/C 扩展点（Gateway 可从本机进程演进为独立服务）。

## 10. 目标系统接入规范

### 10.1 Connector 定义

一个 **Connector** = 一个目标系统的适配单元：

```text
connectors/<system-id>/
  mcp-server/           # 或独立二进制
  openapi.yaml          # 或手工 tool 定义
  skill/SKILL.md        # 领域技能
  policy.yaml           # 级别覆盖、批量阈值
  README.md             # 凭证申请、环境、限制
```

### 10.2 接入门禁（Definition of Ready）

系统进入「可生产」前必须满足：

- [ ] OpenAPI 或等价工具清单评审通过  
- [ ] 每个写工具完成 L 级标注  
- [ ] staging 凭证与 prod 凭证分离  
- [ ] 至少 10 条黄金对话用例（含拒绝、幂等、越权）  
- [ ] 审计字段联调通过  
- [ ] 事故回滚说明已写  

### 10.3 无 API 系统的过渡策略

| 阶段 | 做法 | 可否 prod 写 |
|------|------|--------------|
| T0 | 人工 + 传统后台 | — |
| T1 | 只读：导出/只读库/爬取只读页 | 否 |
| T2 | RPA 写（强确认、小流量） | 极谨慎 |
| T3 | 补 BFF/OpenAPI | 是（切正式方案） |

**政策：RPA 不得作为长期生产写默认。**

## 11. 工具（Tool）设计标准

### 11.1 命名

```text
{domain}_{action}_{object}

例：
  shop_get_order
  shop_search_orders
  shop_refund_order
  shop_start_inventory_sync_job
  shop_get_job
```

- MCP 多服务器时：`shop-admin__shop_refund_order`（与现有 `__` 命名空间一致）  
- 禁止模糊名：`do` / `execute` / `update`  

### 11.2 参数设计

| 规则 | 说明 |
|------|------|
| 强类型 | enum、number、format:uuid |
| 少自由文本 | 原因类字段允许 string，但 L3 必填 |
| 统一身份键 | `order_id` 不要有时 `id` 有时 `orderId` |
| 环境参数 | `env: staging|prod` 或由 connector 实例绑定 |
| 幂等 | 所有 L1+ 写：`client_request_id: string` |
| 批量 | `ids: string[]` + 硬顶；或 `filter` + `limit` 强制 |

### 11.3 返回体标准

```json
{
  "ok": true,
  "receipt_id": "rcpt_...",
  "env": "prod",
  "before": { },
  "after": { },
  "message": "人类可读摘要",
  "undo": { "tool": "shop_reverse_refund", "params": { } },
  "links": { "admin_url": "https://..." }
}
```

失败：

```json
{
  "ok": false,
  "error_code": "ORDER_NOT_REFUNDABLE",
  "message": "当前状态 shipped 不可退款",
  "retryable": false
}
```

### 11.4 最小工具集模板（任意业务系统第一期）

| 工具 | L | 用途 |
|------|---|------|
| `describe_capabilities` | L0 | 能力自描述 |
| `get_resource` | L0 | 详情 |
| `search_resources` | L0 | 搜索 |
| `count_resources` | L0 | 批量预览 |
| `update_resource_low_risk` | L1 | 备注/标签 |
| `transition_status` | L2 | 状态迁移 |
| `preview_mutation` | L0/L1 | dry-run |
| `dangerous_mutation` | L3 | 退款/删除等 |
| `start_job` / `get_job` | L2/L0 | 生产任务 |

总数建议 **第一期 8–20 个**，宁少勿滥；避免 200 个 CRUD 淹没模型。

### 11.5 Progressive Disclosure（工具很多时）

与 Skill 一致：

1. 系统提示只给 **工具名 + 一句话**  
2. 匹配领域后 `skill_read`  
3. 复杂参数说明放 skill 正文  
4. 禁止把整本 OpenAPI 塞进 system prompt

## 12. 技能（Skill）与对话协议

### 12.1 领域 Skill 结构（建议）

```markdown
---
name: shop-admin
description: 电商后台：查单、改状态、退款与同步任务（需确认高危）
always_active: false
---

# 何时使用
...

# 术语表
关单 = status closed；未支付不可发货 ...

# 环境
默认 staging；用户明确「生产/prod」才用 prod

# 标准流程
1) 先 get/search 核实
2) preview（如有）
3) 调写工具
4) 汇报 receipt

# 禁止
- 无 limit 批量
- 编造订单号
- 把完整手机号写入记忆

# 确认话术模板
...
```

归类：③ 用户技能 或 ④ 项目技能；**不是**引擎能力。

### 12.2 对话协议（强制流程）

**标准七步（写路径）：**

1. **澄清** — 对象、环境、范围  
2. **核实** — L0 get/search  
3. **方案** — 将调用的 tool 与预期 after  
4. **确认** — L2/L3 UI  
5. **执行** — 带 client_request_id  
6. **回执** — receipt/job + 链接  
7. **收尾** — 是否需要导出/记一笔（记忆须批准）  

**Give-and-take：**  
若用户要求与业务规则冲突（如「未支付也强制发货」），Agent 应说明张力并给选项，而不是硬调必失败的 API 或绕过。

### 12.3 记忆与进化边界

| 可沉淀（须用户批准） | 禁止沉淀 |
|----------------------|----------|
| 「退款必须先查物流」类流程 | API Token、Cookie |
| 常用筛选口径 | 完整身份证/银行卡 |
| 岗位偏好（简报风格） | 一次性 receipt 当长期事实乱写 |

## 13. 安全 · 身份 · 审计 · 合规

### 13.1 身份模型

```
操作者（人）
  └─ lebi 本地会话
       └─ Connector 凭证（OAuth token / API key）
            └─ 业务系统主体（user/service account）
                 └─ RBAC 允许的动作集合
```

原则：

- **禁止** 默认「超级管理员服务账号」给所有对话用  
- 团队模式（B）必须 **OIDC 到人**  
- 凭证存储：`~/.lebi-ai/connectors/<id>/credentials.toml` 权限 **0600**  

### 13.2 威胁模型（节选）

| 威胁 | 缓解 |
|------|------|
| 提示注入诱导退款 | 封闭工具集 + L3 确认 + 先查后写 |
| 恶意 MCP 包 | 安装确认 + 配额 + 不默认 always_active |
| Token 泄漏进日志 | 指纹化；禁全文 |
| SSRF 打内网 | 网关出站允许列表；禁用通用 web 写内网 |
| 重放攻击 | 幂等键 + 确认 token TTL |
| IM 社工 | allowlist + 写工具不进 IM |
| 内部误操作 | preview + 批量 cap + 环境标识 |

### 13.3 审计字段最低集

```text
timestamp, trace_id, session_id, surface,
actor_id, env, tool_name, risk_level,
params_digest,   # 可脱敏后的参数
confirm_action,  # allow|deny|n/a
upstream_status, receipt_id, ok, error_code
```

保存：Gateway 侧 append-only 日志 + Agent Session JSONL；两者用 `trace_id` 关联。

### 13.4 合规提示（非法律意见）

- 支付/个人敏感信息：最小化展示与落盘  
- 跨境：注意模型 API 出站（对话内容会去 LLM 厂商）— **业务主键与 PII 能少则少**  
- 行业监管：可升级模式 C（变更单）  

**重要：用户消息会发往其配置的 LLM 供应商。**  
生产工单号、客户隐私是否允许出境，需在 Skill/产品提示中明确，必要时对 prompt 做脱敏层（二期）。

## 15. 用户体验与确认流

### 15.1 主路径（桌面 GUI）

1. 设置中启用 Connector、配置 staging/prod 凭证  
2. 顶栏或设置选择 **当前环境**（默认 staging）  
3. 对话发起管理意图  
4. L2/L3 弹出确认卡：  

```text
环境：生产
操作：全额退款
对象：订单 12839
金额：¥128.00
当前状态：paid
结果：将变为 refunded（不可自动撤销）
原因：用户未收到货
[拒绝]  [允许]
```

5. 成功后气泡展示 receipt + 可选「在后台打开」链接  

### 15.2 失败体验

| 错误 | 用户文案方向 |
|------|----------------|
| 401/403 | 无权限或凭证失效 → 去设置 |
| 业务拒绝 | 展示 `error_code` 人话 + 当前状态 |
| 超时 | 可重试；提示幂等不会双写 |
| 需要确认被拒 | 明确「未执行任何变更」 |

### 15.3 无障碍原则

- 确认框 **默认焦点在拒绝/取消**（防回车误允）  
- Esc = Deny  
- 高危不允许「Always Allow」或 Always 仅会话内且不含 L3

## 16. 部署形态与多入口策略

### 16.1 入口能力矩阵

| 能力 | CLI | GUI | Flutter | IM |
|------|-----|-----|---------|-----|
| L0 查询 | ✅ | ✅ | ✅ | ⚠️ 可选只读子集 |

- Connector 出站 HTTPS

## 19. 风险、反模式与缓解

### 19.1 反模式清单

| 反模式 | 后果 | 正确做法 |
|--------|------|----------|
| 模型直连生产 DB | 毁库、无校验 | 仅 API + RBAC |
| 万能 `http_request` | 越权与 SSRF | 封闭 Tool |
| Prompt 当安全边界 | 可被注入 | Policy 引擎 |
| 默认超级 token | 爆炸半径极大 | 最小权限 |
| 无幂等支付 | 双扣款 | idempotency key |
| IM 开放 L3 | 社工 | 白名单 + 禁写 |
| 无 staging | 只能拿 prod 试 | 强制环境 |
| 200+ 扁平工具 | 选错工具 | 精选 + Skill |
| 把密钥写入 memory | 泄漏 | 禁止 |

### 19.2 残余风险

即使方案完整，仍存在：

- LLM 选错工具（靠 skill、枚举、先查后写降低）  
- 用户确认时未读摘要（靠默认焦点拒绝、文案结构化）  
- 上游 API 自身 bug（靠业务测试与灰度）  

**安全是风险降低，不是零风险。** 生产写入必然保留「用户最终责任」——产品文案应诚实。
