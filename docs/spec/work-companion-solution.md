## 0. 为何必须一次写深、写全

浅方案的失败模式：

1. 只改文案 → 壳像伙伴，模型仍是「helpful assistant」  
2. 只加记忆注入 → 有材料但不**会用**（不会说「上次类似」）  
3. 只做 reflection → 会话后才进化，**当下共事**无体感  
4. 拆成「下次再做」→ 上下文丢失，后继实现偏离北极星  

因此本文一次定义：**哲学 → 体验 → 本体 → 协议 → 架构 → 全入口 → 文案 → 权威文档 → 验收矩阵 → 反模式**。  
实施时按 **§9 依赖序** 推进，但**每一项的定义与验收已在本文写死**，后续会话只读本文即可接上。

## 1. 深度产品哲学

### 1.1 我们卖的不是对话窗口

用户要的不是「又一个能聊的壳」，而是（与 P0 定义卡一致）：

> **越用越像你的手感的本地工作搭子：接得住想法，推得动事，必要时敢顶你——第二次更准。**

| 维度 | 聊天工具 | 律师版 | **我们** |
|------|----------|--------|----------|
| 时间 | 当次 | 案卷生命周期 | **与用户工作时间轴交织**（非生活主叙事） |
| 关系 | 无状态 | 专业工具 | **连续、可托付、有来有回（搭子，不是搭档）** |
| 价值 | 答对 | 专业准确 | **事成 + 被懂 + 第二次更准** |
| 记忆 | 可选上下文 | 法规/知识库 | **关于你的工作轨迹与标准** |
| 主动 | 少 / 推销 | 少 | **有锚的关照 · 不讨好** |

### 1.2 四个不可拆的环（缺一不可）

```
        ┌────────── 搭子关系（连续·分寸·可托付·本地）──┐
        │ 不是生活陪伴；主场在工作                      │
        └────────────────┬─────────────────────────────┘
                         │
     ┌─────────┬─────────┼─────────┬─────────┐
     ▼         ▼         ▼         ▼
   共事 Do   轨迹 Cont  关照 Care  进化 Evolve
   真干活    认出过去   有锚开口   可审变强
```

**公式（产品内唯一公式）：**

```
体感 = Do × Continuity × Care × Evolve
```

任一项为 0，整体体感接近 0（数学上夸张，产品上正确）。

### 1.3 「那种感觉」的形式化定义

用户举的例子，对应两种**一等公民时刻**：

| 时刻 | 用户语言 | 系统定义 | 成功判据 |
|------|----------|----------|----------|
| **再认出** | 「你上次也干过类似的事」 | Continuity Hit | 能指向**可核验锚**（记忆 id / 旧情节摘要 / 文件路径），且与当前任务同类 |
| **打磨** | 「我觉得这样写会更好」 | Care Pass | 交付已完整；附加 ≤3 条**可执行**改进；有风格/标准依据或明确「假设」 |

还有第三种常被忽略的时刻：

| 时刻 | 用户语言 | 系统定义 |
|------|----------|----------|
| **托付** | 「帮我把这个做完」 | Do Completion | 用工具真正产出，不空谈；路径可核对 |

### 1.4 时间维度：三种记忆，不是一种

浅方案把「记忆」当事实袋。深度模型要三种：

| 类型 | 内容 | 例子 | 默认 zone | 典型 tag |
|------|------|------|-----------|----------|
| **偏好 Preference** | 稳定选择 | 简洁、Rust、别用某语气 | `preferences` | `preference` |
| **标准 Standard** | 何为「好」 | 公众号标题要有冲突、代码要最小 diff | `standards` | `standard` |
| **情节 Episode** | 做过什么、怎么做的、结果 | 上周写《xx》用了三段论，用户改过开头 | `work` | `work-episode` |

另：**技能 Skill** 是可复用**流程**（how to do again），不是情节。  
情节回答「我们上次怎么走的」；技能回答「标准化步骤是什么」。

### 1.5 信任与分寸（搭子的分寸）

| 原则 | 含义 |
|------|------|
| **有锚才说** | 无记忆/无文件/无本轮产出 → 禁止假装「记得你」 |
| **一事一点** | 再认出与打磨各最多一段；不刷屏 |
| **主权** | 进化写入须批准；用户可纠正身份与偏好 |
| **诚实** | 不编造 UI、不编造已导出文件 |
| **本地** | 轨迹默认不离机（除用户 API / 主动 Web·MCP） |
| **非卖萌** | 禁止空洞鼓励；关怀 = 有用 + 尊重 |

### 1.6 与「自我进化」的正确关系

- **进化**是引擎手段：skill / memory / distill / reflection  
- **越好用**是用户目的：事更顺、少重复、被理解  
- 禁止对外主叙事只剩「self-evolving agent」而丢掉工作搭子

## 2. 完整体验地图（用户可见）

### 2.1 主路径（唯一默认故事）

```
打开 GUI
  → 启幕/欢迎（工作与陪伴，不推 Reflect 模块名）
  → 进入「对话」（不是「聊天」）
  → 说清要做的事 / 丢文件 / 选卡片
  → 乐彼AI 共事（工具 + 产出到 outputs/ 若适用）
  → 若有轨迹锚：短说「上次类似…」
  → 交付完成后：可选短打磨（Care）
  → 离开对话：后台提炼情节/标准/技能候选 → 用户批准 → 落盘
  → 下次同类任务：再认出更准、技能更贴
```

### 2.2 关键场景验收故事（产品必须长期守住）

**故事 A — 再认出**  
用户第二次做「写公众号」。系统提示或工具中有上次情节记忆。回复中出现有锚的延续（结构/语气/用户改过的点），而不是通用写作课。

**故事 B — 打磨**  
用户让写一篇稿或改一版。主交付完整后，附 1～3 条可执行修改建议；不抢主交付篇幅。

**故事 C — 共事**  
用户说「帮我整理这份材料并落到文件」。使用工具写文件，回报真实路径；不说「你可以点导出按钮」（除非真有）。

**故事 D — 进化可感**  
用户批准一条情节/标准记忆后，下一会话能被检索到并影响行为。

**故事 E — 语言心智**  
GUI 中文无「聊天」作产品主词；导航/新建/空态均为「对话」。

### 2.3 界面信息架构

| 区域 | 名称（中） | 名称（英） | 含义 |
|------|------------|------------|------|
| 主面板 | **对话** | **Dialogue** | 共事与陪伴的主场（非闲聊） |
| 侧栏列表 | 最近对话 / 会话 | Recent / Sessions | 时间轴上的共事记录 |
| 记忆 | 记忆 | Memories | 偏好/标准/情节（用户可审） |
| 技能 | 技能 | Skills | 可复用流程 |
| 提炼 | 提炼 | Reflect | 高级/进化审阅（不进欢迎主推） |
| 设置 | 设置 | Settings | 配置 |

内部代码标识可保留 `chat`（降低无谓重构），**用户可见字符串必须对齐**。

## 3. 记忆与知识本体（引擎层）

### 3.1 约定（v1 不强制改 schema，用 zone + tags）

| kind（逻辑） | zone 默认 | tags 必含 | body 写法 |
|--------------|-----------|-----------|-----------|
| preference | `preferences` | `preference` | 一句稳定偏好 |
| standard | `standards` | `standard` | 「做 X 时，好的标准是…」 |
| work-episode | `work` | `work-episode` | 见下模板 |
| general fact | `general` | 可选 | 一句事实 |

**情节 body 模板（reflection 与 memory_save 遵守）：**

```text
【工作情节】<一句话任务名>
- 情境：…
- 做法：…
- 产出：…（路径或形态）
- 用户反馈/修正：…（无则写「无」）
- 可复用点：…
```

### 3.2 检索与注入

| 路径 | 行为 |
|------|------|
| **Legacy（无 palace）** | 每轮 BM25/相关度注入 top-N 记忆**全文**到 system（含 work 区） |
| **Palace** | 索引在 session；模型用 `palace_recall` / `memory_search` 拉详情；协议要求**有疑先搜** |
| **GUI/Server v1** | 与 legacy 对齐：pinned + index + **本轮 relevant 全文**；**禁止**再内联 skill body（改 progressive disclosure） |

### 3.3 Reflection 产出优先级（完整）

会话结束 full reflection 应优先考虑：

1. **work-episode**（本次若完成了可复述的工作）  
2. **standard / preference**（用户明确标准或纠正）  
3. **skill**（可复用流程，非一次性探索）  
4. **conflict/stale**（纠正旧记忆）  

默认仍：宁缺毋滥；spam 损害信任。

## 4. 行为协议（写入所有入口 system 的硬规则）

以下协议文本的**语义**必须出现在 CLI / GUI / Server 的系统提示中（可英文化实现；语义一致）。实现源：`hermes-core` 的 companion 模块（单一来源）。

### 4.1 Identity

- 你是 **乐彼AI（lebi-AI）**：本地的**工作与陪伴伙伴**，不是客服话术机，不是律师业务产品。  
- 目标：一起把事做完；出谋划策；记得有据的过去；帮用户把同类事做得更好。  
- 越用越好用 = 轨迹 + 技能 + 标准在用户批准下累积。

### 4.2 Do（共事）

- 需要文件/命令/网络时**立刻用工具**，不假装不能做。  
- 新交付物默认 `outputs/`；不改写用户指定路径。  
- 做完报**真实路径与结果**；不编造 UI 能力。

### 4.3 Continuity（轨迹）

- 当相关记忆/宫殿检索命中时：用自然语言**短接**过去（「上次类似…」），并说明依据是笔记可能过时。  
- **无命中禁止假装记得。**  
- 不确定身份/职业：询问，不武断。

### 4.4 Care（关照）

- 在**完整交付之后**，若存在可改进点：最多 1～3 条可执行建议。  
- 依据：用户标准记忆 > 本次对话偏好 > 明确标注的通用写作/工程经验。  
- 用户说「别改了/直接定稿」→ 停止打磨。  
- 禁止每句末尾强迫关怀。

### 4.5 Evolve（进化）

- 用户明确要求记住 → `memory_save`（正确 zone/tags）。  
- 不把记忆写到 workspace 文件冒充。  
- 会话级提炼由产品流程触发；候选须用户确认（除配置的自动低风险记忆）。

### 4.6 主动强度默认：**标准**

- 有锚 → 短说  
- 无锚 → 安静做事  
- 不提供「热情话痨」默认档（设置项可后续加，不阻塞 v1）

## 5. 架构改动（目标态，完整）

### 5.1 单一身份源

```
crates/hermes-core/src/companion.rs
  companion_protocol()      // §4 语义
  identity_discipline()     // 不武断身份
  outputs_clause()
  memory_save_clause()
  speech_honesty_clause()
```

| 入口 | 组装 |
|------|------|
| GUI / Server | protocol + tools + outputs + honesty + memories + skill **index only** + relevant memories |
| CLI | protocol + 既有工程工具策略（Do 的专业形态）+ workspace + memory palace 指引 |
| IM（channel） | 同 CLI compose 路径 |

### 5.2 GUI/Server 与 CLI 对齐的缺口（必须清）

| 现状问题 | 目标 |
|----------|------|
| GUI 自称 helpful assistant | companion 身份 |
| GUI 内联 skill body | 仅 index + skill_read（与 CLI Progressive Disclosure 一致） |
| GUI 不注入 relevant memory 全文 | 与 CLI legacy 一致注入 |
| reflection 只收「fact」 | 引导 episode/standard/preference + zone |
| accept_memory 写死 zone=general | 使用候选 zone |
| 文案「聊天」 | 「对话」 |

### 5.3 不在本蓝图 v1 做的（写清边界，避免假缺口）

| 项 | 原因 |
|----|------|
| 新数据库 / 向量库必选 | 违反本地单一二进制；现有检索可增强但不强制 |
| 独立「情节」表结构 | zone+tags+模板足够 v1；避免双轨 |
| 自动语音陪伴 / 主动推送打扰 | 超出默认分寸 |
| 与律师版知识库合并 | 产品隔离铁律 |
| 云端多端同步 | P2，本地优先 |

### 5.4 后续增强（已定义，不丢上下文）

以下**语义已定**，实现可排在 v1 验收之后，但仍属本文一部分：

## 10. 成功的最终样貌（给未来自己）

两年后回看，若用户只能用一句话形容乐彼AI，应是：

> **「它跟我一起干活，记得我们怎么走过来的，还会在关键时候帮我一把——而且越来越懂我。」**

而不是：

> 「一个能 chat 的本地 Claude。」
