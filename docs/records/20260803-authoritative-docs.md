## 0. 用户价值（必填 · 站在用户角度）

- **谁用：** 本仓库的协作者（人类 + AI agent）
- **解决什么痛点：** 仓库此前只有 README / TODO，没有「什么是权威、怎么改、怎么验收」
  的共识层，协作容易各说各话
- **用完后用户多得到什么：** 改任何东西前有明确入口（P0 → P1 → AGENTS）、
  有强制变更流程与台账、有文档位置铁律
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期（读完 AGENTS.md 即可开工）
  - [x] 不增加无意义确认或噪音（仅对「有用户/架构影响」的修改强制台账）
  - [x] 高频路径比改前更快或更省心（入口单一、不再翻找）

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 协作者要新增功能 / 修 bug / 写说明，需要知道产品目标、文档放哪、怎么验收
- **路径变化：** 改前（翻 README / 猜规则 / 文档散落）→ 改后（AGENTS.md 一页总览，
  P0/P1 细则，docs/ 统一索引）
- **成功标准：** 仓库根出现且仅出现 4 个权威 md；新说明可落 docs/ 并在索引登记；
  有用户影响的改动可在 docs/records/ 找到四阶段记录
- **明确不做什么：** 不改任何代码逻辑；不迁移已有 README 的用法章节；不新增第二套产品叙事

---

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** 共识与文档组织层（此前缺失）
- **正确的长期默认路径：** 权威分层 P0 产品法 / P1 开发法 / P2 入口 / P3 简介；
  非权威一律 `docs/`；变更一律台账——与 `codeINDEx/code/small-rust-hermes`
  已实践的体系同构，但内容按本仓库实际（自进化 agent、多入口、bundled/user/project 技能）重写
- **与引擎/各入口边界：** 纯文档改动，不触 crates/clients/scripts
- **安全影响：** 无（未改配置 / 密钥 / server 代码）
- **如何防复发：** AGENTS.md 自检清单 + 文档摆放铁律 + records 台账；根目录
  `TODO.md` 超白名单列为 P0 缺口（见 project-map §6）
- **为何这不是补丁：** 建立的是「共识与流程」本身，是默认路径的起点而非症状处理

## 1. 方案（Plan）

- **目标：** 为本仓库建立与 `code/small-rust-hermes` 同构、但内容自洽的权威文档体系
- **范围：** 做：根目录 3 份新权威文档 + README 入口 + `docs/README.md` +
  `docs/project-map.md` + `docs/records/`（README / 模板 / 本记录）
  **不做：** 改代码、改 README 用法正文、迁移 `TODO.md`
- **用户路径变化：** 改前（无共识层）→ 改后（AGENTS.md 为第一入口）
- **技术要点：** 仅 Markdown；参考 `codeINDEx/code/small-rust-hermes` 的
  `PRODUCT_PRINCIPLES.md` / `DEVELOPMENT_RULES.md` / `AGENTS.md` / `docs/`
  结构，产品内容按本仓库（crates 清单、CLI 子命令、skill 分类、server 安全）重写
- **风险与回滚：** 低；git 可回滚；文档不触运行逻辑
