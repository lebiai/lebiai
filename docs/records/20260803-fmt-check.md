## 0. 用户价值（必填 · 站在用户角度）

- **谁用：** 开发者 / 协作者（人类 + agent）
- **解决什么痛点：** 仓库从未统一格式化，`cargo fmt --check` 必红，CI 无法纳入 fmt；
  diff 里混入格式噪音，代码审查难
- **用完后用户多得到什么：** 代码风格统一；CI 自动拦截未格式化提交，本地与 CI 行为一致
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期（`cargo fmt` 即可对齐）
  - [x] 不增加无意义确认或噪音（只在 push/PR 检查）
  - [x] 高频路径比改前更快或更省心（格式问题自动拦截）

---

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 任何提交 / PR 前后
- **路径变化：** 改前（fmt 未纳入 CI，格式漂移无人管）→ 改后（CI 强制 `cargo fmt --check`）
- **成功标准：** `cargo fmt --check` 全绿；CI 工作流含 fmt 步骤
- **明确不做什么：** 不改任何业务逻辑；不改前端 TS/Dart 格式（本主题仅 Rust fmt）

---

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** 工具链纪律层（无格式基线 + 无自动检查）
- **正确的长期默认路径：** 一次全仓 `cargo fmt` 建立基线，CI 以 `cargo fmt --check`
  防回归；与既有 check/clippy/test 硬门槛并列
- **与引擎/各入口边界：** 覆盖全部 Rust crates（含 hermes-gui）；TS/Dart 前端不在
  本主题范围
- **安全影响：** 无（纯格式）
- **如何防复发：** CI 步骤 + P1「lint / test 硬门槛」扩展为含 fmt
- **为何这不是补丁：** 建立格式基线 + 自动化防线，一次性收敛而非逐文件特判

## 1. 方案（Plan）

- **目标：** `cargo fmt --check` 全绿 + CI 纳入 fmt
- **范围：** 做：`cargo fmt`（全工作区）、`.github/workflows/ci.yml` 加
  `cargo fmt --check`。**不做：** 逻辑改动；TS/Dart 格式化
- **用户路径变化：** 见 0b
- **技术要点：** rustfmt 默认配置（无 rustfmt.toml 则用官方默认）
- **风险与回滚：** 低；格式化 diff 较大但纯机械；git 可回滚
- **方案确认：** [x] 已对照 P0/P1（含第七条）· 日期/人：2026-08-03 / Codex
