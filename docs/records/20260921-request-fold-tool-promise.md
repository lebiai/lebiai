## 0-fp. 第一性原理（必填 · P0 第零条）

**拒绝的类比：**「整读 700 行之后模型还是去补后半段 —— 这是**模型的行为**，契约里再写死一句『读完不回头』就好」。
这个类比的错处：它把「模型没照做」当成**模型的性格问题**，于是解法落在**更严的措辞**上。
真问题是：**它照做了，我们没给它整份。**

**拆出的真（实跑会话逐字取证，`/tmp/lebi-idx/sessions/2026-09-21T14-39-48-*.jsonl`）：**
- 它**确实**按契约整读了一次成品（一次 `read`，无 offset）；
- 请求体装配时，这条结果被**悄悄砍到前 20,000 字**，末尾补一句
  「[……原始输出共 37428 字，这里只把前 20000 字发给你；会话文件里仍是全文……]」；
- 于是它的思考里写的是（原文）：**「The read got truncated at 20000 chars. I need the rest.」**
  对外说的是：「成品 728 行，**一次读不全（工具截断在前 20000 字）**。续读后半段，一次读完。」
- **它不是不听话 —— 它在补齐被砍掉的那一半。** 我们上一批的结论（「引擎没截断，是模型行为」）是**错的**：
  那次查的是**会话文件**（落盘的永远是原文），没有查**发给请求体的那一份**。

**如何从真推出做法（两件，与「加一句契约」无关）：**
1. **引擎侧上限必须 ≥ 工具自己承诺的单次返回。** 这条规矩本来就已经写在代码注释里
   （`RequestFold::recent_chars`：「**上限不许低于工具自己的承诺**」），但当初只按 `web_fetch` 那一个
   工具取了 20,000 —— `read` 的承诺是**整份文件**（默认 2000 行，实测一份成品 37,428 字），
   `bash` 的承诺是 **30,000**。**规矩在，值不对。**
2. **工具的单次承诺必须是个有限的数，超了要自己给「继续读的把手」。** `read` 现在没有上限：
   文件多大就吐多大。给它一个明确上限，超了在**行边界**切开并写明 `offset=`，模型照着续读即可 ——
   这样「一次读不完」是**工具说出来的**，不是引擎**偷偷砍的**。

**为什么不再加契约：** 契约已经写了「整读一次成品 / 读完不回头」，而模型做到了它那一半。
**引擎的义务是让守信的人办得成事**，不是再罚他一顿。

## 0. 用户价值（必填 · 站在用户角度）

- **谁用：** 项目组里的用户（GUI 对话 / 项目组会话），这一批直接受益的是吕老师那一棒。
- **解决什么痛点：** 用户连着两天抱怨**慢** —— 而「慢」里有一大块是**来回搬运同一份字**：
  引擎把 37,428 字的成品砍成 20,000 字发过去 → 模型**只能再读一次**拿剩下的 17,466 字 →
  同样的字节在网络上走两趟、绕两次模型往返。**引擎的省字，反而让总账变贵。**
- **用完后用户多得到什么：**
  - 吕老师**一次读全、一次判完**（不再出现「续读后半段」这一步）；
  - 少一次模型往返（实测 11 次工具调用里就有 1 次是纯浪费）；
  - 顺手把 `bash` / `source_read` 同族的「悄悄砍」一起收掉：模型不再拿到残缺的东西当完整的用。
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期（用户可见面**一个像素没动**）
  - [x] 不增加无意义确认或噪音
  - [x] 主操作一眼能找；空/载/错态完整
  - [x] 高频路径步骤少、界面干净（这次是**更少**：少一次续读）

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 用户说「出这一期」，吕老师整读成品、报题。
- **怎么走完：** 用户**看不到任何变化**。改的只有盘面下的两件事：
  ① 吕老师这次**真的读到了整份**（不再有「续读后半段」）；② 超长文件由 **`read` 自己**说明怎么接着读，
  而不是引擎背后砍掉。
- **看起来怎么样：** 对话里吕老师的话会少一句「工具截断在前 20000 字」。选题单、成稿、索引三份文件的
  格式**一字不改**。
- **空 / 载 / 错态：**
  - 文件超过单次上限 → **工具**明说切在第几行、用 `offset=` 接着读（模型据此续读，用户看得出这是在按页读）；
  - 单个文件大到必须分很多次 → 每次都有把手，模型不会瞎猜边界；
  - 读数取不到 → 老规矩，记一笔，不编。
- **好走 / 好看：** 无新增操作、无新增界面。**少一个来回**就是这一批的「好看」。
- **成功标准：** 吕老师那一棒 **一次 `read` 读全成品、不再出现续读**；`bash`（承诺 30,000）
  接下来的那一轮**不再被砍到 20,000**；成品与选题单格式一字不改。
- **明确不做什么：** 不动索引与 ID 方案；不改工具对外承诺的**行为**（`read` 的 `limit` 默认仍是 2000 行）；
  不给用户加设置项；不为省字把窗口调小。

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** 请求体装配（`hermes-core::compaction::fold_for_request`）。
- **根因（一处，两半）：**
  1. `RequestFold::default().recent_chars = 20_000` 是**照着一个工具**（`web_fetch`）抄的数，
     而它注释里自己写着「**上限不许低于工具自己的承诺**」—— **`read`（整份文件）与 `bash`（30,000）
     都在这个数之上，于是每一条超过 20,000 字的正当结果都被砍**，模型只能重取；
  2. `read` 没有单次承诺上限，所以「工具承诺」这个量在它身上是**未定义**的，无法被上面那条规矩覆盖。
- **正确的长期默认路径：**
  - 引擎侧**一个**数：`MAX_TOOL_RESULT_CHARS`（= 折叠最近窗口的上限 = 工具单次返回上限），
    取 64,000（**≥ 一件正当的单次读取**：实测一天成品 37,428 字，留 1.7× 的余量给忙的一天）；
  - 工具侧**登记制**：会吐正文的工具在**一处**登记自己的单次上限
    （`hermes-tools::TOOL_RESULT_CEILINGS`），一条测试断言 `≤ MAX_TOOL_RESULT_CHARS`，
    超了当场红 —— 新工具吐正文忘了登记，绳子上就有一个显眼的缺口；
  - `read` 超过上限时**在行边界切开**并写明 `offset=`（把手在工具手里，不在引擎背后）。
- **与引擎/各入口边界：** 判据只在 `hermes-core::compaction`（唯一出口，四个入口共用）；修理只在
  `hermes-tools` 的工具内部。**不为某个入口 fork 一份折叠逻辑。**
- **安全影响：** 无。请求体可能变大（最多到工具承诺值），属**本来该发**的内容。
- **如何防复发：**
  - 跨 crate 的绳子从「只有 `web_fetch` 一条」升级为**登记表 + 一条断言**（新工具漏登记有名可查）；
  - `read` 的分页把手有单测（超限切开 → 行号连续 → `offset` 指得对）；
  - 台账里把「上一批的错结论」更正并写明**错在哪一步查**（查了落盘件、没查请求体），
    下次查「模型为什么没照做」时先看**它实际收到的是什么**。
- **为何这不是补丁：** 治的是「**引擎背着工具砍内容**」这个根因，做法是让**工具**拥有并声明自己的
  单次上限、让**引擎**的上限由这条声明推出；不是给某一次报错加特判，也不是再加一句契约措辞。

## 1. 方案（Plan）

- **目标：** 让「工具刚给模型的东西」**完整到达模型**；超出单次上限时，由**工具**带把手分页，而不是引擎悄悄砍。
- **范围：**
  - **做：** ① `hermes-core::compaction` 加 `MAX_TOOL_RESULT_CHARS`（64,000）并作为 `RequestFold::recent_chars`；
    ② `hermes-tools` 加 `TOOL_RESULT_CEILINGS` 登记表 + 跨 crate 断言；③ `read` 加单次上限 + 行边界分页把手；
    ④ `source_read` 的 12,000 截断补一句「已截断」的实话（同族：不许悄悄砍）。
  - **不做：** 不改 `RequestFold` 的窗口条数（40）与「更早的整段省略」；不改 `web_fetch`/`bash` 的承诺值；
    不动 ID/索引方案；不动 GUI 可见面；不加设置项。
- **用户路径变化：** **无**（吕老师少一次续读，用户看到的话少一句）。
- **技术要点：** `crates/hermes-core/src/compaction.rs`、`crates/hermes-tools/src/{lib,read,source,web_fetch}.rs`。
- **风险与回滚：** 风险 = 请求体变大 → 更慢/更贵。压法：上限取「一件正当读取」而不是无限；
  更早的历史仍整段省略；`bash`/`web_fetch` 的承诺值不动。回滚 = 还原 `recent_chars` 一个数 + `read` 的切分。
- **方案确认：** [x] 已对照 P0/P1（含第七条）· 2026-09-21 · 用户「开工」

## 2. 实施（Implement）

- **实际改动摘要：** 四个文件，都是「一个数 + 一根绳子 + 一个把手」，没有新增运行时分支。

| 文件 | 改动 |
|---|---|
| `crates/hermes-core/src/compaction.rs` | 新增 `MAX_TOOL_RESULT_CHARS = 64_000`（引擎给「一次工具调用」的返回上限，写清取值来由）；`RequestFold::default().recent_chars` 由写死的 `20_000` 改为**它**（同一个数、一份真相）；`RequestFold` 的文档从「= web_fetch 的默认值」改为「= 登记表里最大的那个承诺」 |
| `crates/hermes-tools/src/lib.rs` | 新增 `pub const TOOL_RESULT_CEILINGS: &[(&str, usize)]` —— **会吐正文的工具在一处登记自己的单次上限**（`read` / `bash` / `web_fetch` / `source_read`），并写明「新工具吐正文就在这里登记一行」；新增断言 `the_request_fold_never_under_cuts_a_tool_promise`（每个承诺 ≤ 引擎上限；工具名不重、不为空） |
| `crates/hermes-tools/src/read.rs` | 新增 `MAX_READ_CHARS = hermes_core::compaction::MAX_TOOL_RESULT_CHARS`；一次 `read` 超过它时**在行边界切开**，尾巴写 `... (还有 N 行；用 offset=X 继续读)`；头一行本身就超预算的病态文件（压缩过的 JSON）单独处理，也把行号与 `offset` 说清楚；`limit` 先切的情况改成**同一句把手**（删掉旧的 `... (N more lines)`，它没告诉模型怎么接着读）；`spec()` 的描述补一句「超长文件尾巴会给 offset」。新增 3 条单测 |
| `crates/hermes-tools/src/{bash,web_fetch,source}.rs` | `bash::MAX_OUTPUT_CHARS`、`web_fetch::default_max_chars()` 变 `pub` 供登记表引用（`default_max_chars` 同时变 `const fn`）；`source.rs` 的 `12_000` 提成 `MAX_SOURCE_CHARS`，并**补一句实话**：原文超过它时附「原文共 N 字，这里只给前 12000 字」（原来悄悄砍，模型会把残缺当完整用）。`web_fetch` 里那条**只拴一个工具**的旧绳子（`the_request_fold_never_under_cuts_what_this_tool_promises`）删掉——它已被登记表那条更宽的断言覆盖，留两份就是第二份真相 |

- **关键路径/文件：** `hermes-core::compaction`（判据唯一出口，四个入口共用）+ `hermes-tools` 各工具内部。**不为某个入口 fork 一份折叠逻辑。**
- **偏离方案处：** 追加了 `source_read` 的「已截断」实话（同族：不许悄悄砍）与 `read` 的 `limit` 先切那句把手（原方案只写了「超字符上限」那一种切法，实现时发现旧的 `... (N more lines)` 一样没给把手，一并改掉）。除此无偏离。
