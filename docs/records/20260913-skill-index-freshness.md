## 0-fp. 第一性原理（必填 · P0 第零条）

- **拒绝的类比：** 不是「重启一下就好了」，不是「别的 App 也要重启」，也不是
  「技能是启动时加载的，这是设定」。拒绝把「进程快照」当成「技能数据的正常生命周期」。
- **拆出的真：**
  1. GUI 在**进程启动时**把技能索引读进内存一次（`gui/src/state.rs:283`），此后每个回合、
     每个会话都只是**克隆这份快照**（`gui/src/commands/chat.rs:117`）。全仓检索确认：
     `state.skills` 除启动那次写入外**没有任何刷新点**。
     所以真相不是「新会话不算数」，而是**任何会话都不算数，一直要到重启 App**。
  2. 同一个进程里，技能面板走 `commands/skills.rs:40` 的**每次读盘**，于是
     **用户看得到新技能、模型看不到**。用户无法自查，只能猜「触发词写错了」。
  3. 紧挨着的记忆却是**每回合从磁盘重读**（`chat.rs:119`，注释写明
     "so mid-session memory_save is visible next turn"）。同类数据两种保鲜度 →
     这是**实现遗漏**，不是设计选择。
  4. server 同病：启动快照（`server/src/state.rs:146`）+ 每请求克隆
     （`server/src/routes/chat.rs:168`）。
  5. prompt 里的技能索引只渲染 `name: description`
     （`hermes-channel/src/companion_context.rs:139`），**`triggers` 不进 prompt**。
     所以「把触发词写进描述」有效，「补 `triggers` 字段」对发现无效（它只喂
     `relevance.rs` 的 `skill_bag` 打分）。
- **如何从真推出：** 真 3 → 技能必须与记忆**共用同一条保鲜规则**：每次组装回合上下文时
  从 store 重读，读失败则退回上次已知列表。真 1 → 只在 `skill_create` 后失效缓存**不够**：
  缓存本身就是根因，而且 `SKILL.md` 会被编辑器 / Finder 手改，事件式失效覆盖不到。
  真 5 → 本期**不动 prompt 渲染**：描述里已经带触发词，够用；加 triggers 渲染是另一件事。

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 用户在会话 A 让搭子建了个技能；回到会话 B（或就在同一会话下一句）喊触发词。
- **怎么走完：** **不需要任何额外动作**，直接喊。技能面板看到的 = 模型知道的。
- **看起来怎么样：** **用户可见面零变化**。不新增控件、不改文案、不改提示。
- **空 / 载 / 错态：**
  - 空：一个技能都没有 → 与现状一致（索引块不渲染）。
  - 载：每回合读一次目录，无 spinner、无阻塞感（与记忆同量级开销）。
  - 错：读盘失败（权限 / 目录被删）→ **沿用上次已知列表**，不报错、不空窗、不打断对话。
- **成功标准：** 新建 / 编辑技能后**不重启 App**，下一条消息即可命中；手改 `SKILL.md`
  描述同样立即生效。
- **明确不做什么：**
  - 不改 prompt 结构、不新增 `triggers` 渲染
  - 不做技能目录文件监听（watch）
  - 不改 CLI 的「会话启动加载」语义（另记遗留）
  - 不改技能面板 / 安装 / 删除行为

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** 缓存生命周期（配置层）——**进程级快照被当成会话级数据用**。
- **正确的长期默认路径：** 技能索引与记忆索引共用同一条规则：组装回合上下文时
  `store.list()` 重读，失败退回上次已知。刷新点收敛为**每个入口一个 `refresh_skills()`**；
  「读新 + 兜底旧值」的规则写在**引擎层一个函数**里，GUI / server 不各写一套
  （P0：共享引擎，不 fork 平行逻辑）。
- **与引擎 / 各入口边界：**
  - `hermes-skills`：新增 `list_or_cached(store, cached)`（可单测，无 Tauri 依赖）。
  - GUI：`AppState::refresh_skills()`，用在 `commands/chat.rs:117` 与 `state.rs:377`。
  - server：同构 `AppState::refresh_skills()`，用在 `routes/chat.rs:168`。
  - CLI：不动（其刷新点是会话启动，新会话本来就读新；见遗留项）。
- **成本：** 每回合一次 `read_dir` + 解析 N 个小 frontmatter（当前 11 个），与记忆每回合
  重读同量级；相对一次 LLM 调用可忽略。
- **安全影响：** 无。技能仍是本机明文，不含 token / 密钥；不新增出站。

## 1. 方案（Plan）

- **目标：** 技能索引与记忆同一条保鲜规则——新建 / 编辑技能后无需重启，下一个回合即可用。
- **范围：**
  - **做：** 引擎层 `list_or_cached` + 单测；GUI / server 各一个 `refresh_skills()` 与 3 处
    调用点；真机目视由用户重启后自测。
  - **不做：** prompt 结构 / triggers 渲染、文件监听、CLI 语义、技能面板行为、
    技能安装与删除逻辑。
- **用户路径变化：** 改前 = 建完技能 ⇒ 重启 App 才能用（且用户不知道要重启）；
  改后 = 建完就能用。少一步，且不再误导。
- **技术要点：** `crates/hermes-skills/src/store.rs`（+`lib.rs` 导出）、
  `crates/hermes-gui/src/state.rs`、`crates/hermes-gui/src/commands/chat.rs`、
  `crates/hermes-server/src/state.rs`、`crates/hermes-server/src/routes/chat.rs`。
- **风险与回滚：** 风险 = 每回合多一次读盘（可忽略）；读盘失败已兜底，不会比现状更差。
  回滚 = 还原上述 5 个文件。
- **方案确认：** [x] 已对照 P0/P1（含第七条）· 日期/人：2026-09-13 / Codex

## 2. 实施（Implement）

- **实际改动摘要：**
  1. **引擎层** `hermes-skills/src/store.rs`：新增
     `list_or_cached(store, cached) -> Vec<LoadedSkill>` —— 读新，读失败则退回上次已知；
     `lib.rs` 导出。规则只有这一份，GUI / server 不各写一套。
  2. **GUI** `state.rs`：新增 `AppState::refresh_skills()`（读新 + 回写 `state.skills`）。
     两处调用点改走它：`commands/chat.rs`（对话每回合，紧挨记忆重读那几行）、
     `state.rs::build_serve_ctx`（IM / ServeCtx 组装）。
  3. **server** `state.rs`：同构新增 `refresh_skills()`；`routes/chat.rs` 的每请求取值改走它。
  4. `state.skills` 字段保留，角色从「唯一真相」变为**「上次已知」兜底**；启动时那次
     `skill_store.list()` 保留为初值。CLI 未动（见遗留项 1）。
- **偏离方案处：** 无
