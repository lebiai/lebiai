## 0-fp. 第一性原理（必填 · P0 第零条）

  1. 不是「再来一遍 8/07 那篇文章」。上一版基于 **`git HEAD`**；今天工作树有 ~101 项未提交改动，

  2. 不是「把 agent 的输出贴成文档」。子代理报告是证词，不是结论：本次区分 **[亲验]** 与 **[子代理]** 两类。
  3. 不是「用一次扫描代替长期机制」。快照是**会过期的**（H 类），过期条目**不得覆盖 P0**。
- **拆出的真：**
  1. 协作痛点是「**当前工作树 ≠ 提交历史**」：personas / topics / scoped memory / outputs 四层新东西全在未提交区，
     而台账 `20260914-personas.md:7` 还写「待开工」——**纸面与磁盘不一致**，这是本次最贵的错。
  2. 用户要完成的不是「读一遍代码」，是「**下次改动不踩坑**」：需要可引用的文件:行号 + 已知坑位，
     而不是架构散文。
  3. 数据在哪：本地明文 `~/.lebi-ai`；本次只读，未碰任何用户数据、未起 GUI、未连网。
  4. 谁说了算：**产品（用户）说了算**——本次发现的问题不代签、不改代码、不改 P0；清单交产品裁决。
  5. 这一步实际发生什么：权威文档精读 → 6 个并行只读子代理逐 crate 深读 → 本人**抽查关键断言** → 实测 `cargo check/test` → 落盘。
  6. 用户看见什么：`docs/snapshot/codebase-learning.md` 一份，附录级别可查；无产品界面变化。
- **如何从真推出：**
  - 真 1 → 快照必须显式标注「基线 = 工作树」，并列出 WIP 新增模块与台账不符处（§5.B2）。

  - 真 4 → 不写「已修复」，只写「已核实的问题」；授权与私钥两条明确标「需产品决策」。
  - 真 5 → 亲验项与子代理项分标；亲验覆盖最贵的断言（构建/测试/协议/授权/未接线）。

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 新会话 / 新协作者开工前，要判断「这仓库现在到底长什么样、能不能编译、哪些是纸面哪些是真的」。
- **怎么走完：** 打开 `docs/snapshot/codebase-learning.md` → 先看 §1「实测状态」与 §5「问题清单」→ 再到 §4 按子系统精读 →
  需要动某个 crate 时看 §7「新人必知」。**三步内能定位到自己要改的那一层。**
- **看起来怎么样：** 分级标题 + 表格 + 每条带行号；未验证的标 [子代理]；过期事项在文首明示「行号针对工作树」。
  空态不适用（文档）；错误态 = 读者若按 HEAD 复现行号会偏移 → 文首已写明。
- **好走 / 好看：** 结论在 §1/§5，细节在 §4；高危项排最前（A 安全 → B 不实 → …）而不是按目录顺序。
- **成功标准：** 读者能说出「工作树有 WIP、构建与测试全绿、personas 只在引擎、签名私钥在仓库里」四件事。
- **明确不做什么：** 不改任何产品代码；不动 P0/P1/AGENTS；不把发现的问题写成「已修复」；不代产品裁决授权范围。
