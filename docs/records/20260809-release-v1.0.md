## 0. 用户价值

- **谁用：** 所有从 GitHub Releases 下载安装包的新老用户。
- **解决什么痛点：** 版本号各处不一致（Cargo 0.1.1 / package.json 0.1.0）、Release 页没有说明、用户不知道下载哪个、也不清楚 1.0 有什么。
- **用完后用户多得到什么：** 一个明确的 1.0：一处版本、一份用户向发布说明、Release 页直接下载 macOS dmg 与 Windows exe、安装指引齐全。
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期（下载 → 安装 → 填写 Key → 开工）
  - [x] 不增加无意义确认或噪音
  - [x] 高频路径比改前更省心

## 0b. 产品经理视角

- **场景：** 用户打开 GitHub Releases 页面找安装包。
- **路径变化：** 推送 `v1.0.0` tag → CI 自动构建 macOS dmg + Windows exe → 自动挂到 Release v1.0.0，正文为 `docs/release-notes.md`（用户向 1.0 说明 + 安装 + 隐私）。手动触发默认 tag 也改为 v1.0.0。
- **成功标准：** Release 页有说明、有 2 个安装包附件、版本号全仓一致 1.0.0。
- **明确不做什么：** 不做签名/公证（文档已注明为后续分发事项）；不改产品功能。

---

## 0c. 架构师视角

- **根因：** 版本分散在 workspace Cargo.toml / tauri.conf.json / ui package.json，历史遗留 0.1.1 与 0.1.0 不一致；Release 无说明正文。
- **正确的长期默认路径：** 以 workspace `Cargo.toml` 为唯一版本源，`tauri.conf.json` 与 `ui/package.json` 对齐；发布说明作为仓库文件 `docs/release-notes.md`，CI 通过 `body_path` 注入 Release 正文（每次发版更新该文件即可，随 git 版本化、可审查）。
- **边界：** CI 只构建+挂载，不签名；安装包内 markitdown sidecar 两侧均已捆绑。
- **如何防复发：** 发布清单（台账 §2）列出三处版本文件；CI 的 `body_path` 保证正文不会空。
- **为何这不是补丁：** 把「发版」从手工散落操作收敛为「一个 tag + 一份说明 + 一次自动构建」的固定路径。

- **发布清单：**
  1. `Cargo.toml` version = 1.0.0
  2. `crates/hermes-gui/tauri.conf.json` version = 1.0.0

  4. `Cargo.lock` 随 `cargo check` 重新生成
  5. `docs/release-notes.md` 写入并提交
  6. 推 `v1.0.0` tag → `release.yml` 自动出 dmg + exe 并挂载
