## 0-fp. 第一性原理（P0 第零条）

- **拒绝的类比：**
  1. 不是「别人家的产品也压缩、也会重复，所以正常」——用户付的是本地工作搭子的账，丢上下文就是丢工作。
  2. 不是「流式是前端动画问题，调调滚动就行」——先把「引擎到屏幕每一环是否真在走」查清，再决定改哪一环。
  3. 不是「token 花得多就调小 max_tokens」——慢的成因是**同一段历史被重发 25 次**，不是单次请求过大。
- **拆出的真：**
  1. 用户的活动上下文 = 模型这一轮真正看见的东西。它一旦被折成空白，用户的工作历史**在模型眼里就消失了**，而磁盘上还有全文——「文件没丢」不等于「它还记得」。
  2. 记忆是用户教给搭子的长期资产。同一套标准被记三遍，等于下次要用时它得在三份措辞里猜哪份是准的。
  3. 感知时延 = 首字可见时间。答案在写、但视口没跟着走，用户看到的就是「卡住，然后一整段跳出来」。
  4. 一轮干活最多 25 次 LLM 往返（`max_tool_rounds`），**每次往返都重发整段历史**；单条工具输出实测 24,170 token。
- **如何从真推出：**
  - 空白摘要不许落盘（宁可这一轮不压，也不要删前缀）；
  - 同一「首行」的记忆视为同一件事，写前拒绝并指路用 supersedes 合并；
  - 跟随判据用「用户本来就在底部」+ 节流，而不是依赖变化时滚一次；
  - 发给模型的历史按「旧的折叠、最近的限量截断」重建，**落盘一字不动**。

## 0b. 产品经理视角

- **场景：** 用户在项目组 / 工位里连续干活；一次「小王干活」式的回合里模型要调几十次工具。
- **怎么走完：** 用户发一句 → 立刻看见字在长（或看见工具卡）→ 答案写完落成一条消息。失败时：压缩失败 → 按原历史继续，不提示错误、不丢前缀。
- **看起来怎么样：** 不变。不新增面板、不新增设置项；「更早的日子」等既有层级不动。
- **好走 / 好看：** 没有新步骤。用户唯一能感到的变化是「更快看见第一个字」。
- **成功标准：** ① 长会话里不再出现空白摘要落盘；② 同一首行的第二、三条标准写不进「它记得的」；③ 生成中视口跟随（上滑即停止跟随）；④ 单轮 input token 明显下降。
- **明确不做什么：** 不改 P0 主路径、不加配置项、不动记忆优先级（pin 原文 > 卡 > 按需取回）。数据清理只动「明确是垃圾」的 8 条，且**先备份再移走**（`memories/.trash-20260918/`，移回即恢复）。

## 0c. 架构师视角

- **根因层级：** ① 压缩（状态机缺少「摘要无效」这一态）；② 记忆写入闸门（判据只在工具路径，长度稀释了余弦）；③ UI 滚动（效应依赖错了变量）；④ 引擎 turn 循环（请求体 = 全量历史，无预算）。
- **正确的长期默认路径：** 判据各收一处——`compact_session` 守卫空白摘要；`FsMemoryStore::near_duplicate_impl` 守首行重复；`hermes_core::compaction::fold_tool_outputs_for_request` 守请求体预算（**落盘不动**）；`ChatView` 跟随只在贴底时生效。
- **与引擎/各入口边界：** 折叠与压缩都放在 `hermes-core`，四个入口（GUI/CLI/agent/server）共用；turn 循环改动落在 `hermes-turn`，因此 CLI/server/IM 同样受益，不为 GUI 另开平行逻辑。
- **安全影响：** 无——不碰 token / TLS / 0600；工具输出仍完整落盘，模型侧只少看重复字节。
- **如何防复发：** 每条都配单测：空白摘要 → `Err` 且消息一条不少；同首行 → `Conflict`；`fold_tool_outputs_for_request` 不动原数组、超限必带指路标记。
- **为何这不是补丁：** 四处都是「把判据放回它该在的那一层」，而不是给症状加 if。

## 0d. 追加发现：被行分隔符劈开的消息（本轮自查中发现，含我自己造成的一次损坏）

- **现象：** 同一个真实会话文件里有 4 行不是合法 JSON：一条用户消息横跨两行（另一条横跨三行，中间还夹一个空行）。`read_session` 当时对坏行只 `tracing::warn!` 然后 `continue`，于是**这段用户亲口说的标准被静默丢掉**——这正是「记不住」的另一半。
- **根因（两层）：**
  1. **脆弱性来自 U+2028 / U+2029（Unicode 行分隔符 / 段分隔符）。** 用户从微信 / Word 粘过来的文本带这两个码位；`serde_json` 认为它们在字符串里合法，就原样写进文件。文件本身是合法 JSON，但**任何按 Unicode 行边界切分的工具**（python 的 `str.splitlines()`、多数编辑器的批量编辑）都会把它当换行，一条事件立刻被劈成多行。
  2. **这次的具体损坏是我自己造成的。** 本轮删除那条空白压缩记录时用的 python 脚本走了 `splitlines()` + `join('\n')`，把原文里的 U+2028 落成了真实换行 → 两条用户消息被劈开、读回时丢失。已备份证据：`*.jsonl.bak-20260918-line-separator-split`（含 3 处原始 U+2028）与更早的 `*.bak-20260918-blank-compaction`（干净，无坏行）。**这是事故，不是天灾，向用户交代。**
- **从真推出的做法（不是补丁）：**
  - **写入端收口**：`encode_event()` 成为落盘编码的唯一入口（`SessionWriter::append` / `rewrite_session` / `update_session_title`），落盘前把 U+2028 / U+2029 换成 `\n` 转义——语义不变，文件从此对任何工具都安全。旧文件被 `update_session_title` 顺带重写时同样被规范化。
  - **读取端自愈**：`read_events()` 在「这行自己不是完整事件」时与下一行拼接重试（拼接用 `\n` 转义）；每次拼之前先确认下一行不是独立事件，**一条坏行只丢它自己**，不会吞掉后面整段会话；拼不回来才丢弃并如实计数写进 warn。`read_session`（正读）与 `recall_in_session`（翻旧账）共用同一实现。
  - **数据修复**：坏行拼接回单行（用 `\n` 转义），先备份再改；文件 290 条事件 → 288 条（两条被劈开的各还原成一条）。
- **不做：** `read_flow` 保持「只扫接力行」的快速路径（手写一条记录 + 短字符串），不改成全量解析——组会话很长，这是它存在的理由；被劈开的接力记录本次数据里不存在，写入端收口后也不会再有。
