## 0-fp. 第一性原理（必填 · P0 第零条）

- **拒绝的类比：** 不是「400 就重发一次」「给 provider 加个重试」，也不是「把窗口调大一点碰巧躲开」。
  更不是把责任推给模型（「王海燕规则写坏了」）——模型只发了工具调用，配对是引擎的账。
- **拆出的真：**
  1. 请求体预算按**条数**算（`fold_for_request`），而「哪几条是一组」由**工具往返**决定：
     一条 assistant(`tool_calls`) + 紧随其后的若干 `role:"tool"` 回复是一个不可分割的单位。
  2. 切在单位中间时，线上格式（OpenAI 兼容）的首条就是 `role:"tool"`，端点判它「没有前驱
     `tool_calls`」，直接 400（DeepSeek 原话见本记录标题行）。
  3. 起点的条数奇偶会被**只在内存里**的引擎消息改变：写文件后的 `[lebi-AI Care]`、工具预算收尾那条
     都是引擎自己 push 的，落盘时被 `for_persist` 过滤掉。所以磁盘上的会话永远看着「配对完好」，
     故障只出现在请求体里，且时好时坏。
  4. 会话文件的形状不是判据；**发出去的那一份**才是。
- **如何从真推出：** 预算可以丢消息，但不能切开一个工具往返。起点落在「工具结果」上时，
  把开启它的那条 assistant 一起带进窗口（配对完整、信息不丢）。这修的是窗口的**边界规则**，
  不是某次 400 的症状。

## 0. 用户价值（必填 · 站在用户角度）

- **谁用：** 桌面 GUI 里跑长活的工位与项目组会话（本次是财富早知道的王海燕）。
- **解决什么痛点：** 干了十几轮工具、文件也写出来了，最后一轮突然 400，整轮白干、看不到回话。
- **用完后用户多得到什么：** 长会话照常出结果；不再因为「写得越久越容易炸」而丢一轮活。
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期（用户侧零操作差异，只是不再失败）
  - [x] 不增加无意义确认或噪音
  - [x] 主操作一眼能找；空/载/错态不变
  - [x] 高频路径步骤少、界面干净

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 用户在「财富早知道」说一句开工，王海燕要采一天的情报、落盘、再交下一棒。
- **怎么走完：** 说话 → 看她一轮轮采集（过程照旧可看）→ 情报文件出现在产出里 → 有回话。
  **本次修复不改变任何一步**，只让最后一步不再以 400 收场。
- **看起来怎么样：** 没有新增界面、没有新增按钮、没有新增弹窗。用户能感知的唯一变化是
  「长活跑到底了」。
- **好走 / 好看：** 不引入任何新面；失败提示沿用既有「一句人话」的口径（不喊红叉）。
- **成功标准：** 复跑一次王海燕的采集，跑到写文件、再跑到 40 条以上消息之后仍然有回话。
- **明确不做什么：** 不改窗口大小、不改工具轮数上限、不改王海燕规则、不新增重试层。

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** 协议层（请求体的消息配对），不是 UI、不是模型、不是权限。
- **正确的长期默认路径：** 判据落在**唯一**一处 `hermes-core::compaction::fold_for_request`——
  窗口起点由「条数」升级为「条数 + 工具往返边界」。各入口（GUI / CLI / server / IM）继续共用它。
- **与引擎/各入口边界：** 只动 `hermes-core`，GUI / CLI / server / IM 无需各自修；`run_turn` 的两处
  fold 调用（普通往返与收尾那条）自动继承。
- **安全影响：** 无。请求体略大（最多多带开启工具的 1–2 条）；不涉及 token、TLS、本地明文。
- **如何防复发：**
  - 新用例扫「写文件 → 引擎催促 → 继续干活」这段形状的多个长度（42 / 46 / 50 …），
    断言**折叠后第一条真消息不许是工具结果**——回退到按条数切时这两条用例会红。
  - 旧用例 `older_messages_are_omitted_from_the_request` 调整成起点不落在工具结果上的形状，
    保住它「省略 + 窗口内截断」的原意；配对规则由新用例单独守。
- **为何这不是补丁：** 修的是「窗口边界怎么算」这条规则本身，症状（某一次 400）随之消失；
  没有加 retry、没有加特判、没有改窗口大小。

## 1. 方案（Plan）

- **目标：** 请求体窗口不许切开一次工具往返。
- **范围：**
  - **做：** `window_start`（起点落在工具结果上就往前挪到开启它的 assistant）；两条新用例；
    调整一条旧用例的形状。
  - **不做：** 改 `RequestFold` 的窗口大小 / 截断上限；改 `sanitize_history_for_provider`；
    改 `hermes-turn` 的催促消息；改落盘。
- **用户路径变化：** 无（改前 → 改后 用户看不见任何界面上/步骤上的差别）。
- **技术要点：** `crates/hermes-core/src/compaction.rs`。
- **风险与回滚：** 起点最多往前多带 1–2 条（极端历史下可能更多），请求体略大；不可能因此丢配对。
  回滚 = 恢复 `messages.len().saturating_sub(fold.keep_recent_messages)`。
- **方案确认：** [x] 已对照 P0/P1（含第七条）· 2026-09-20

## 5. 附注

**证据链（本次诊断）：**

- 真实会话文件（`LEBI_DATA_DIR` 数据根）33 条消息、24 次工具调用、零孤儿 —— 磁盘上看不出问题。
- 用真实 `fold_for_request` 跑的探针（复用仓库 target，`/tmp/lebi-probe`）：
  - 无引擎催促：len=41 → 窗口起点 `Assistant(ToolUse)` ✓
  - 有引擎催促（写文件后那条）：len=44 → 窗口起点 **`User(ToolResult)`** ✗ → 线上格式首条即 `role:"tool"`
  - 同一条催促：`for_persist` 落盘为空 / `is_internal_instruction_text` 为真 —— 所以它不落盘。
- 修复后同一探针：两种情况都是 `Assistant(ToolUse)`。

**为什么一开始没被兜住：** `sanitize_history_for_provider` 只在开轮时跑一次（GUI 发送入口），
而 fold 在**每一次模型往返前**跑（`hermes-turn`）——折叠切出来的孤儿在 sanitize 之后才产生。
