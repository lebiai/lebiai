## 0-fp. 第一性原理

- **拒绝的类比：** 不是「再给某个入口加一层 try/except」；也不是「让用户重开会话绕过去」
  （真实经历：用户靠点开别的会话再切回来，问题就消失了——这说明病根不在用户操作）。
- **拆出的真：** 引擎对自己发出去的消息**没有「能不能发」的判据**。它只校验过「工具配对」，
  没校验过「这条消息序列化后还剩不剩东西」。一条空 assistant 在线格式里退化成
  `{"role":"assistant"}`，端点必然拒收；而它一旦进了会话（哪怕是只在内存里），
  **之后每一次请求都带上它**——所以错误不是一次性的，是持续的。
- **如何从真推出：** 立一个判据（`Message::has_sendable_content`），在三个位置各用一次：
  ① 产出处不把空的一轮留进历史（并给用户一句人话）；② 历史修复时丢掉它（覆盖 GUI/server/IM/载入）；
  ③ 落线前兜底（覆盖 CLI 等不走修复的入口）。

## 0. 用户价值

- **谁用：** 所有人（GUI / CLI / 手机 / IM）。今天的现场：财富早知道里「交给吕老师」。
- **解决什么痛点：** 点一下，0.2 秒后就报错；连点五次都报；切个会话再回来又好了——
  用户完全无法理解，也无法自己绕过。
- **用完后用户多得到什么：** 这种消息不会再被发出去；而且**这一轮没产出时用户看得见原因**
  （「输出在 16384 tokens 处被上限截断，说一句继续或拆小」），不再是空白回复。
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期
  - [x] 不增加无意义确认或噪音
  - [x] 空/载/错态完整（错态改成一句人话，不喊红叉）
  - [x] 高频路径步骤少、界面干净

## 0b. 产品经理视角

- **场景：** 用户在一段长会话里（几十轮工具往返、上下文很大）催一棒干活。
- **怎么走完：** 正常路径不变。异常路径：模型这一轮什么都没产出时，对话里出现一句
  「（这一轮没能产出内容：输出在 N tokens 处被上限截断。再说一句「继续」，或者把这一步拆小一点。）」，
  用户说一句继续即可。
- **看起来怎么样：** 不是红叉、不是空白，是一句人话；会话可以继续用下去，不必重开或切走。
- **成功标准：** 同一段会话里，空轮次之后再发一句仍能正常得到回复（今天不是这样）。
- **明确不做什么：** 不改 `max_tokens`；不做请求体/响应落盘；不动「谁在说」的判据。

## 0c. 架构师视角

- **根因层级：** 协议层（消息 → 线格式的可序列化前提）。不是工具、不是人物定义、不是项目组装配。
- **证据链：**
  1. 报错逐字：`HTTP 400 … "Invalid assistant message: content or tool_calls must be set"`，
     2026-09-20 14:40:31–14:47:31 共 **6 次**，每次都在用户发出后 0.13–0.43 秒失败（请求体被拒）。
  2. 种子那一轮 `usage = input 66795 / output 16383`（`max_tokens = 16384`，输出顶格），
     且那一段**没有任何 assistant 消息落盘**——`for_persist` 对空内容跳过，消息只活在内存里
     （`crates/hermes-gui/src/commands/chat.rs:651` 先 push、`:654` 才跳过落盘）。
  3. 每轮开头的历史修复对 assistant 分支**无条件 push**（`crates/hermes-core/src/message.rs` 原 161-173），
     兜不住它；落线时 `content: None` + `skip_serializing_if` 把两个字段都省掉 → 非法体。
  4. 自愈对照：用户 14:47:36 / 14:47:41 点开两个新会话再切回（会话从磁盘重建），
     下一次请求干净——吕老师随即一口气产出《选题单》（14:50，28412 B，`decision` 已记）。
- **正确的长期默认路径：** 「能不能发」只有一个判据，产出处、修复处、落线处共用它。
- **与引擎/各入口边界：** 判据放 `hermes-core::message`（所有人共用）；修复沿用既有
  `sanitize_history_for_provider`；落线兜底在 `hermes-llm`（provider 侧，跨厂商通用）。
- **安全影响：** 无。
- **如何防复发：** 三条测试钉住（判据真值表 / 修复丢空 assistant / 落线不产生空 assistant）。
- **为何这不是补丁：** 补的是「消息能不能发」这个缺失的前提，而不是拦某一次报错。

## 1. 方案（Plan）

- **目标：** 空 assistant 不再进请求体；空轮次给用户一句人话。
- **范围：** 做 —— 判据 + 三处使用 + 测试 + 台账。
  **不做** —— 改 max_tokens、请求/响应落盘、GUI 日志落文件（列为遗留项）。
- **用户路径变化：** 改前 = 持续 400、只能切会话自救；改后 = 正常继续；空轮次有说明。
- **技术要点：** `crates/hermes-core/src/message.rs`、`crates/hermes-llm/src/openai.rs`、
  `crates/hermes-turn/src/lib.rs`。
- **风险与回滚：** 低。若某厂商**要求** assistant 必须出现（罕见），表现为少了一条空消息，不影响语义。
- **方案确认：** [x] 已对照 P0/P1 · 2026-09-20 · 用户指令「1 吕老师的工作全都报错」

## 2. 实施（Implement）

- `message.rs`：新增 `Message::has_sendable_content()`（文本非空且非引擎内令 / 工具块在自己这一侧 /
  图片算 / 思考块不算）；`sanitize_history_for_provider` 的 assistant 分支改为「有内容才 push」。
- `openai.rs`：`translate_outbound` 的 assistant 分支，空消息直接返回空 vec（CLI 等不走修复的入口）。
- `hermes-turn`：一轮无产出时不 push 空 assistant，改 push 一句人话并同时流给界面。
- **偏离方案处：** 无。
