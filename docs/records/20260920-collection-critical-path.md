## 0-fp. 第一性原理（必填 · P0 第零条）

- **拒绝的类比：** 不是「把并发数再调大一点」；不是「给慢的站加超时」；不是「再塞一个重试子代理」；
  也不是「把内容砍短让用户少看一点」。
- **拆出的真：**
  1. **墙钟 = 最慢那条子代理的耗时**，其余都白等。所以问题从来不是「总工作量」，而是
     **工作量摊得匀不匀**。三条子代理分别产 8,499 / 10,652 / 14,294 个输出 token，
     最慢那条一个人占了 **43%** —— 这就是 143.7 秒的来源。
  2. **子代理的耗时 ≈ 它自己吐出来的 token 数 ÷ 吞吐（实测约 100–134 tok/s）**。
     不是站点数、不是网络延迟。子代理每看一个站都要在**一条 token 流里**serial 地想一遍，
     所以「多派几条、每条少看几个站」是唯一能真正压墙钟的杠杆。
  3. **一份内容被生成几次，决定这一棒贵不贵。** 用户看不见「生成」这件事，
     只看得见秒数；而每一份 26KB 的卷，生一次约 20–30 秒。
  4. **能被 `bash`/`awk` 确定性地算出来的东西，不该让模型再想一遍**：
     接栏、按链接去重、数 A/B/C —— 这些是字符串操作，不是判断。
  5. 「同一份名单在文件里出现两遍、两遍还不一样」不是文风问题，是**执行事故**：
     上一轮实测里，这一处矛盾让主循环公开地"想"了十几秒，最后**自己猜了 18 个站的入口**。

- **如何从真推出：**
  1 + 2 → 把 3 条子代理拆成 **7 条**，每条约 5–7 个站，让最长的那条约 55–70 秒（而不是 143.7 秒）。
  3 → 整卷正文**只在子代理那边生成一次**（子代理各自写自己那份 `_parts/*.md`），
      主循环**不重写、不重排**；对话里那一份是 `read` 回来的副本，不是第二次创作。
  4 → 接栏 + 去重 + 统计行全部收进**一条 `bash`**，主循环这一层不再有 `read 整卷 → 逐条 edit` 的回合。
  5 → 名单**只保留一份**，每一行都带实测过的入口与取法；子代理不再有"猜"的空间。

## 0. 用户价值（必填 · 站在用户角度）

- **谁用：** 在《财富早知道》或工位里说「干活」，等王海燕交资讯卷的人。
- **解决什么痛点：** ① 一轮 4 分钟，用户盯着屏幕干等；② 最慢的那条子代理决定一切，
  另外两条早就回完了；③ 主循环在尾巴上又读又改又重写，**用户在这 75 秒里看不到任何新增**；
  ④ 名单自相矛盾，模型猜入口 —— 猜对了是运气，猜错了就是"这站没用"。
- **用完后用户多得到什么：** 同一份卷、同样的格式、同样的"对话里逐条可见"，
  但等待时间从约 4 分钟降到约 2 分钟量级。
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库（纯提示词层改动）
  - [x] 步骤可感知（工具卡上并排 7 张「子代理」）
  - [x] 不增加无意义确认
  - [x] 空/载/错态：某一块没产出 → 卷里留一行「本栏本轮未产出」，不挡住整卷
  - [x] 高频路径步骤更少：主循环从 4 步（接栏 / 读卷 / 去重 / 补统计）压到 **2 步**（一条 bash / 交卷）

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 用户进「财富早知道」，说「干活」。没有别的动作，没有别的配置。
- **怎么走完：**
  1. 海燕确认窗口（默认当日北京时间）→ **一条回复里同时发出 7 张「子代理」卡**；
  2. 7 条子代理各自抓自己那一小块、各自把成品写进 `outputs/<日期>/_parts/<块名>.md`，
     各自只回一行（文件路径｜条数｜A/B/C｜拿不到几个站）；
  3. 海燕**出一条 `bash`**：按栏接块 → 按原文链接去重 → 补文末统计行 → 打印首尾；
  4. 海燕 `read` 一眼整卷，**逐字**把这份清单贴进对话。
- **看起来怎么样：** 用户看到的是一排 7 张子代理卡同时在跑；主会话里没有网页正文，
  只有 7 行交卷 + 一条 bash + 最后那份清单。
- **好走 / 好看：** 用户全程不用点任何东西。第一屏在 20 秒内就动起来（7 张卡出现），
  而不是过去那种"发了三个、等两分钟、然后又是两分钟的静默"。
- **成功标准：** 整轮墙钟 **≤ 180 秒**（当前 241 秒）；对话里条目数与卷内条目数**相等**；
  来源分布里前两名之外的站点也有条目。
- **明确不做什么：**
  - 不做定时任务、不自动起跑；
  - 不加"失败重试子代理"（见 §4 遗留 1：它是一条**串行**回合，实测代价 40–60 秒，
    而用户当前第一诉求是快）；
  - 不改三栏结构、不改条目那三行、不动 A/B/C 判据；
  - 不让子代理再派子代理（引擎硬约束）。

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** **提示词层**（人物定义），不是引擎。
  上一批已经把引擎侧的结构修好了（子代理真并发、工具面只认本轮宿主、截断不再收工），
  本批**不改任何 Rust 代码**。这是刻意的：先把"派活的形状"改对，再谈引擎。
- **先量了一遍，再动手（这是本批最重要的一步）。**
  `subagent` 的返回值里**本来就带 telemetry**（`duration_ms` / `input_tokens` / `output_tokens` /
  `tool_calls`），会话 `.jsonl` 里也有每一条 `at` 时间戳。三份历史运行摆在一起：

  | 运行 | 头（确认窗口 + 写工单） | 并行段（最慢子代理） | 尾（主循环自己干） | 墙钟 |
  |---|---|---|---|---|
  | 基线：子代理**返回文本**，父写卷 | 30.1s | 94.0s（三条 39.1 / 59.5 / 94.0） | **117.1s** | 241.2s |
  | 四栏：子代理**落盘**，父接栏 | 61.7s | 120.0s（四条） | 47.9s | 229.6s |
  | 三栏：子代理**落盘**，父接栏（现行 0.7.0） | 21.9s | **143.7s**（63.6 / 111.2 / 143.7） | 75.1s | **240.7s** |

  三条结论（都有实测数字支撑）：
  1. **"子代理落盘 + 父接栏"确实治好了尾（116 → 48–75s）**，这部分要留；
  2. 但**并行段涨了**（94 → 143.7s），因为落盘那条子代理要多吐一份 JSON 转义过的正文，
     并且它的**输出 token 从 23,244 涨到 33,445**；
  3. **尾还剩 75 秒**，其中约 35 秒花在「读整卷 → 逐条 `edit` 去重」上，
     而这段还踩了一个真坑：**同一文件上并行发 3 条 `edit`，只有最后一条落盘**
     （上一轮实测原话："前两条被覆盖了"）—— 那是**内容错误**，不只是慢。
- **正确的长期默认路径：**
  1. **摊匀**：7 条子代理，按「块」而不是「栏」派活；块名进文件名，栏由 `bash` 接的时候再贴。
  2. **一份内容只生成一次**：子代理写 `_parts/`，主循环一个字的正文都不写。
  3. **确定性的活交给 `bash`**：接栏、按链接去重、数 A/B/C、写统计行，全部一条命令完成。
  4. **名单只有一份**，每行带入口 + 取法（实测过的才写进去）。
- **与引擎/各入口边界：** 只改 `hermes-core` 的人物定义与团队定义；
  GUI / CLI / server / IM 行为不变，因为它们共用同一份人物定义。
- **安全影响：** 无新增。子代理仍用父会话同一套 `PermissionChecker`；
  并发仍在引擎的 `max_concurrent = 8` 之内（本批派 7）。
- **如何防复发：**
  - 名单只有一处，`rg` 就能核对是不是又长出第二份；
  - 人物定义里写死"**正文不许在主循环生成**"，并附上实测代价（约 30 秒 / 整卷）；
  - telemetry 已经在 `subagent` 的返回值里，下一次不用猜：直接看 `duration_ms` 与 `output_tokens`。
- **为何这不是补丁：**
  - 不是给某一条子代理调参，是把"派活的形状"从 3 条重划成 7 条；
  - 不是给慢站加超时，是让最慢的那条**本来就没那么慢**；
  - 不是把 `edit` 冲突"处理掉"，是**取消主循环在尾部的整段编辑回合**。
- **旧账要认：** 0.7.0 里写过一句"**别再往下拆**，拆成两栏实测 99.7s / 96.4s 不如整块 94s"。
  那句话是**被污染的**：它比的是"跨运行"（解锁版 0.7.0 的四条 vs 基线的三条），
  而且那两条子代理**都带 `write`**（都要多吐一份正文），拆法还把同一批站点切得头重脚轻。
  本批换成**同一口径**：看 `output_tokens` 与 `duration_ms` 的比例，用 7 条重新摊平。旧结论作废。
