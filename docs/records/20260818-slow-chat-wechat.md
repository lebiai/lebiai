## 0-fp. 第一性原理

- **拒绝的类比：** 不是「模型变慢了所以加 loading」；不是「微信丢了所以再同步一遍」。
- **拆出的真：**
  1. 桌面回复和后台整理（离开会话蒸馏、微信空闲蒸馏）共用同一个 API Key / 同一家模型。后台先占用，你看见的字就慢。
  2. 微信 JSONL 一直在 `~/.lebi-ai/sessions/wechat/`，没有删。侧栏先只留 50 条桌面对话，8 月 6–7 日的微信被挤出列表；即使补回，也会埋在「更早」里找不到。
- **如何从真推出：** 对话占用模型时后台必须让路；微信在侧栏有自己的一组，不跟桌面抢 50 名额，也不混在更早里。

---

## 0. 用户价值

- **谁用：** 桌面 GUI 用户
- **解决什么痛点：** 刚开窗 / 刚换对话，字出得很慢；找微信记录以为丢了
- **用完后用户多得到什么：** 正在看的回复先出字；左侧能直接看到「微信」一组
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库
  - [x] 步骤可感知、可预期
  - [x] 不增加无意义确认或噪音
  - [x] 主操作一眼能找；空/载/错态完整
  - [x] 高频路径步骤少、界面干净

---

## 0b. 产品经理视角

- **场景：** 打开乐彼AI 说话；打开左侧「最近对话」找微信
- **怎么走完：** 左侧今天 / 昨天下面有「微信」；点开只能看，回消息仍在微信里。说话时后台整理等你说完
- **看起来怎么样：** 「微信」是和今天/昨天同级的小标题；条目标题仍是「微信消息 · 月日 时:分」
- **好走 / 好看：** 不用滚完 50 条桌面对话；不用搜才找得到
- **成功标准：** 5 条 8 月 6–7 日微信记录出现在「微信」下；新开对话首字不再被启动蒸馏拖住
- **明确不做什么：** 不从云端再拉微信；不把微信写成可在桌面续聊；不改模型本身的速度

---

## 0c. 架构师视角

- **根因层级：** 调度（同一 provider 并发）+ 列表策略（50 条桌面封顶 + 按日分组）
- **正确的长期默认路径：** 实时对话登记 `LiveLlmGate`；蒸馏 / micro / 离开整理先 `wait_idle`。列表桌面封顶 50，渠道记录另附。UI 按 `channel === wechat` 单独成组。
- **与引擎/各入口边界：** 只动 GUI 调度与侧栏。磁盘 JSONL 不动。IM 发送仍 fail-closed。
- **安全影响：** 无
- **如何防复发：** 渠道行不参与 50 截断；purge 跳过渠道路径；后台 LLM 必须等 `live_llm`
- **为何这不是补丁：** 默认路径改成「对话优先 + 微信单独成组」，不是给某一天的文件加白名单

---

## 1. 方案

- **目标：** 正在看的回复先用模型；微信记录在侧栏找得到
- **范围：** GUI `LiveLlmGate`、离开/微信蒸馏让路、侧栏微信分组。不做：换模型、重拉微信、桌面续聊微信
- **用户路径变化：** 微信从「更早」底部 → 独立「微信」组；启动后约 90 秒内不跑蒸馏
- **技术要点：** `state.rs` LiveLlmGate；`chat.rs` 进/出闸；`reflect.rs` / `micro.rs` wait_idle；`session.rs` 渠道行不截断；`sessionTime.ts` wechat 组
- **风险与回滚：** 蒸馏推迟，收件箱稍晚到。可接受。
- **方案确认：** [x] 已对照 P0/P1 · 2026-08-18
