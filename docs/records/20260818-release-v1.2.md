## 0-fp. 第一性原理

- **拒绝的类比：** 不是另起发版流程；不是在发布说明里把「点更新」写成已经能用。
- **拆出的真：** 更新器必须先装进应用，再发一版，概览才会出现「更新」。这一版是带更新器的安装包。
- **如何推出：** 升 1.2.0；说明写清「这一版带更新器，下一版才能点」；推 main + `v1.2.0`。私钥不进 git，走 Actions secrets。

## 0. 用户价值

GitHub 可下 1.2 的 dmg / exe。装上之后，设置概览能看见版本；再往后的版本可以在设置里点更新。

## 0b–0c

沿用 `release.yml`。构建 job 需要 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。`body_path` 必须是 `docs/releases/release-notes.md`。

## 1. 方案

版本三处对齐 1.2.0；重写发布说明；提交更新器实现 + 发版改动；推 main；打 `v1.2.0`。

## 2. 实施

见本次提交与 tag。

## 3–4

CI 通过且 Release 挂上 dmg、exe、`.sig`、`latest.json` 后改为已验收。真机「点更新」要等再发一版（U3 后半）。

## 5. 第一次 tag CI 失败（2026-08-18）

run `32114134041`：macOS DMG 9m48s 失败；Windows NSIS 11m42s 失败；Publish 被跳过。

对照上次成功的 1.1：macOS 13m35s、Windows 25m27s。这次短一截，两边都死在「Build DMG / Build NSIS」——也就是开始要签名更新器包的那一步。

本机用 `~/.tauri/lebi-ai.key` 能打出 1.2.0 dmg + `.sig`，所以代码和密钥本身没问题。

结论：GitHub runner 上 `TAURI_SIGNING_PRIVATE_KEY` 多半是空的（没注入）。常见原因：建在 Variables / Environment secrets，而不是 Repository Actions secrets；或只建了名字没贴全文。

已加 `scripts/check-updater-secrets.sh`，重跑时第一步只报 `key_len` / `pass_len`。
