## 0-fp. 第一性原理（必填 · P0 第零条）

- **拒绝的类比：** 不是「人多热闹、岗位齐全才像团队」；不是把审稿、称重、编目硬塞进栏目，好让每个人都有事做。
- **拆出的真：** 这张桌子要交的是一期能念的口播稿。用户说死了就四步：获取信息、挑选新闻、梳理成稿、生成口播稿。不在这四步里的人坐在桌上，只会多一次交接、多一个「等他」。工位还在——扫地僧、雨天、小文日常 1:1 照旧；拿掉的是桌上的座位，不是人。
- **如何从真推出：** 组定义只留四人，对上四步：王海燕采、吕老师选（接口人）、小宋写、小雨念。组规正文改成这四步。侧栏工位名单不动。接力 / 点头机制这轮不改。

## 0. 用户价值（必填 · 站在用户角度）

- **谁用：** 桌面 GUI，点开「财富早知道」做一天一期口播稿的人。
- **解决什么痛点：** 桌上七个人，三个人不在「采 → 选 → 写 → 念」里，名册、交接、组块都还在喊他们。
- **用完后用户多得到什么：** 名册一眼四人四步；「交给…」只列这四人；提示词不再把称重 / 审 / 编目当成这一期必经的棒。
- **好用性自检：**
  - [x] 不需要额外运行时 / 数据库

  - [x] 不增加无意义确认或噪音

## 0b. 产品经理视角（必填 · 禁止跳过）

- **场景：** 用户点侧栏「财富早知道」，要做今天这一期口播稿。
- **怎么走完：** 看见组名 + 桌上 4 人 → 王海燕采料 → 吕老师报题、用户点头 → 小宋成稿 → 小雨出口播稿。缺人仍显示缺席，不静默。
- **看起来怎么样：** 顶部名册四人；「交给…」四行；侧栏工位里扫地僧 / 雨天 / 小文还在，只是不出现在这张桌的名册里。
- **好走 / 好看：** 少三个人、少三棒；不改 EpisodeBar 的点头 / 接力交互，只改谁坐在桌上。
- **成功标准：** 组定义成员 = 这四人；缺席测试不再拿雨天当桌上的人；侧栏点扫地僧 / 雨天 / 小文仍是工位。
- **明确不做什么：** 不下线这三人的工位；不改授权码结构；不重做接力 / 点头；不改 P0。

## 0c. 架构师视角（必填 · 禁止修修补补）

- **根因层级：** 组编制写在 `teams/caifu-zaozhidao.md`（编译进二进制）。桌上有谁、组块怎么写、交接能交给谁，都从这份名册派生。人多不是 UI 问题。
- **正确的长期默认路径：** 组定义 = 栏目流水线。工位定义 = 人 + 手艺。一个人可以有工位而不坐某张桌。
- **与引擎/各入口边界：** 改 `hermes-core` 的 team 真源；GUI / server 读同一份 `team::all()`。人物 `SOURCES` 不动。
- **安全影响：** 无。
- **如何防复发：** 组块 / 缺席 / 接力测试改成用还在桌上的人（小雨 / 小宋 / 王海燕）；历史台账不改写。
- **为何这不是补丁：** 编制从「七个岗位」收到「四步四人」，真源改一处，引用跟着改。
