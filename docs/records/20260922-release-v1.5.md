## 0-fp. 第一性原理

- **拒绝的类比：** 不是把十几天的改动塞进 1.4 的包（客户端会拿不到新契约）；不是在说明里写没实现的能力
  （侧栏增删改人物、一键切过去、输入框提示语跟人物变——这三条这一版都没有）。
- **拆出的真：** 1.4 之后的工作树里躺着**一整层新东西**（项目组与接力、团队名册与授权按人物开关、
  采集的名单/窗口/格式、审稿标准 V1.0、按 ID 取料、口播契约），它们**已经互相依赖**——
  契约文本是 `include_str!` 编进二进制的，少发一版，客户端拿到的就是旧契约。客户要的是
  **一个能装、能配 Key、能开项目组干活的包**，那就必须换版本号、换说明、换 tag。
- **如何推出：** 升 1.5.0（四处对齐）→ 重写 `docs/releases/release-notes.md`
  （只写本版真有，并把「明确没做的」列出来）→ 全量门禁 → 推 `main` → 打 `v1.5.0` →
  `release.yml` 在 macos-14 / windows-latest 上产出 dmg / NSIS setup.exe 并挂 Release。

## 3b. CI 第一次红的定位与收口（2026-09-22 18:39 那一轮）

**现象：** `Release Installers`（run 35717091194）里 **macOS DMG** 失败在 `Build DMG (universal…)`，
注解是 `Process completed with exit code 127`；`Windows EXE (NSIS)` 随后也失败。`publish` 需要两个 job 都成，
所以**没有任何 Release 被创建**（安全：可以重打 tag）。

**根因（读代码得到，不是猜日志 —— 日志要 admin 权限）：** 127 = 命令找不到，而这一轮唯一新增的是
「通用包」两处改动，两处各有真 bug：

1. **`scripts/prepare-markitdown-bundle.sh` 生成的 wrapper 写死解释器路径**
   `PY="$ROOT/python/bin/python3.12"`。解释器是构建机上的 `uv` / `python3 -m venv` 现装的，
   minor 版本随机器变（本机 3.12、CI 上装到 3.13 就可能），取不到就走 wrapper 自己的
   `exit 127`（那是「bundle 不完整」的约定码，于是整步以 127 收场，看不出是它）。
   改法：wrapper 运行时**扫 `python/bin/python3.*`**，取第一个可执行的；缺失时仍 127，但报错把目录说清。
   已用「假 3.13 目录」实测：有解释器 → 正常 exec；删掉解释器 → `exit 127` 且信息可读。
2. **`.github/workflows/release.yml` 的上传路径没跟着 `--target` 走**
   通用包落在 `target/<triple>/release/bundle/`，而上传只写 `target/release/bundle/` ——
   就算构建成功，下一步也会撞 `if-no-files-found: error`。改法：两种前缀都收。

**同一轮里「不是我们引入的」那条：** `CI`（ubuntu `cargo test`）仍是红的（exit 101）——
v1.4 台账就记过它自 2026-08-18 `9f64eed` 起连续未绿；本机 macOS `cargo test --workspace` 全绿。**与本轮无关。**

**收口方式：** 修完提交 → **重打 tag `v1.5.0`**（`git tag -f` + `push -f`）→ 让 `release.yml` 重跑。
之所以敢重打而不是升 1.5.1：`publish` 没跑过，`v1.5.0` 这个 Release 从没被创建，客户端无从拿到「旧的 1.5.0」。

**已知限制（本轮不修，留给下一版）：** 通用 `.app` 里那份 vendored python 仍是**构建机架构**（arm64）。
Intel Mac 装通用包**能开**，但「文档导入」这条链在 Intel 上可能不可用（要真双架构得把两种解释器都塞进去）。
这条写进验收遗留项。

## 3c. CI 第二次红的定位（2026-09-22 19:01 那一轮 · run 35719164043）

**现象：** 重打 tag 后 `release.yml` 重跑 —— **`Windows EXE (NSIS)` 全绿**（NSIS + updater 资产上传成功），
**`macOS DMG` 仍红**，死在同一步 `Build DMG (universal, Apple Silicon + Intel)`（耗时 281s，
注解只有 `exit code 1`）。`publish` 依旧被跳过，仍无 Release（安全）。

**已排除的：**

1. **不是缺解释器了** —— 上一轮的 127 消失，`Prepare markitdown sidecar` 这条链在 Windows job 上实测通过（64s）。
2. **不是脚本/代码本身** —— 本机 `TAURI_TARGET=universal-apple-darwin scripts/build-dmg.sh` **端到端跑通**：
   `lebi-AI_1.5.0_universal.dmg`（144M）+ `lebi-AI.app.tar.gz` + `.sig`，
   `lipo -info` 确认二进制是 `x86_64 arm64` 真通用包。
3. **不是磁盘耗尽** —— 本机整个 target 约 8.3G；而 CI 从 cargo 开始到挂掉只有 ~2-3 分钟，
   这个时间窗内 x86_64 那一支连依赖都编不完，不可能在磁盘写满时挂。
4. **不是 `latest.json` 的命名** —— `scripts/write-latest-json.sh` 早就把 `darwin-aarch64` 与
   `darwin-x86_64` 两个键都指向同一份 `.app.tar.gz`，通用包不改变这个契约。

**卡点：** 这个仓库的 job 日志下载接口要 admin 权限（本机无 token），界面上只剩 `exit code 1`，
**猜不下去**。所以本轮不猜，先加一条**可读的诊断**：macOS 构建步骤把 stdout 落盘，
失败时把**日志尾部 30 行**逐行转成 `::error::` annotation（外加 `df -h` 快照转 `::warning::`）——
annotation 走 check-runs API 可读，这是本仓库唯一能拿到失败原文的通道。
拿到原文再定因、再修，符合「不修修补补、不碰运气」。

## 3d. macOS 通用包真因与修复（2026-09-22 20:20 那一轮 · run 35725218151）

**拿到原文的方式：** §3c 加的诊断生效了 —— 构建步骤把日志落盘，失败时交给
`scripts/ci-annotate-log.sh`，把「报错行 + 日志尾部 + 磁盘」压进**一条** annotation
（`%0A` 转义，绕开 `::error::` 每个 check run 只显示十来条的上限；API 可读）。

**原文（这才是真因）：**

```
resource path `resources/markitdown-sidecar/python/lib/python3.14/site-packages` doesn't exist
warning: build failed, waiting for other jobs to finish...
Error failed to build aarch64-apple-darwin binary: failed to build app
```

**根因：** `scripts/prepare-markitdown-bundle.sh` 用 `cp -R "$BASE_PREFIX" "$OUT/python"`
把解释器前缀整体搬进 bundle —— **`cp -R` 原样保留符号链接**。本机走 `uv`
（python-build-standalone，链接都是相对的、指得回来），CI 上没有 `uv`，走
`python3 -m venv`（Homebrew python 3.14），前缀里那条
`lib/python3.14/site-packages` 在别的机器上是**悬空链接**。
tauri 打包时按 `resources/**/*` 的 glob 逐个校验资源，撞上悬空链接就报
`resource path ... doesn't exist`，直接打死整轮构建 —— 所以 CI 死得快（~5 分钟）、
日志尾部全是 `cargo:rerun-if-changed=` 噪声，报错埋在 3000 行中间。

**修法（根因，不是特判）：** prepare 脚本里新增 **Canonicalise** 一步 ——
`cp -R` 之后**规范化解释器树**：能解析的符号链接落成实体文件，悬空的直接删掉
（构建机残渣，运行时用不到：wrapper 只认 `$OUT/python/bin/python3.*` 与 `$OUT/site-packages`）。
并把验收标准写死在同一步里：**规范化之后 bundle 里不该再有任何符号链接**，
还剩就 `exit 1`（不再让它烂到 tauri 那一步才炸）。
`prepare-markitdown-bundle.sh --force` 本机实测：`dereferenced=9 dropped-dangling=0 left=0`，
`markitdown 0.1.6` 仍可跑；fixture 实测（绝对链接 / 相对链接 / 悬空链接各一）
→ `dereferenced=2 dropped-dangling=2 left=0`。

**同轮顺手止血（基础设施抖动，不是我们的 bug）：** run 35723740592 那轮死在
`Add the Intel target`（`rustup target add x86_64-apple-darwin` 一分钟超时 —— 下载 std 的网络抖动），
后面构建步被跳过，整轮白等 12 分钟。这一步现在：已装就跳过、没装重试三次、失败照样出可读 annotation。

**另外两处早就排除的：** 磁盘（CI 上 `35Gi` 可用）、`latest.json` 命名（两个 darwin arch 指向同一份
`.app.tar.gz`，通用包不改这个契约）。
